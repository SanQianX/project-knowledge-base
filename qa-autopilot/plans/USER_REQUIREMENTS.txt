**发现问题 → 真实复现 → 根因分析 → 最小修复 → 自动测试 → GitHub 提交 → 回归验证 → 工程清理 → 再次验证 → 下一轮测试。**

所谓持续运行，是通过外部调度器、持久化状态和自动恢复实现，而不是无限制地让模型不断输出和修改代码。

# 四、最高优先级的安全原则

必须将以下原则作为整个开发包的强制约束。

## 4.1 功能保护优先

任何 Bug 修复、代码清理、格式规范化或性能优化，都不得无理由改变现有业务功能。

必须区分：

- 明确的 Bug。
- 设计上允许的行为。
- 未完成的新功能。
- 代码质量问题。
- 测试环境自身的问题。
- 产品设计需要人工判断的问题。

不能将所有不符合 Agent 预期的结果都判断为 Bug。

## 4.2 数据安全优先

禁止：

- 删除真实用户知识数据。
- 清空用户配置或历史记录。
- 覆盖模型凭据。
- 破坏已有 Git Hook。
- 修改未知第三方配置。
- 删除不明确用途的数据目录。
- 随意重建索引并破坏有效知识。
- 清理正在运行的进程所使用的文件。
- 因测试失败就重置真实用户环境。

所有破坏性测试必须使用独立测试数据和隔离环境。

## 4.3 不允许伪造测试成功

禁止：

- 删除失败的测试。
- 注释掉正确断言。
- 将真实 E2E 偷换为 Mock 测试。
- 用接口 HTTP 200 代替业务成功。
- 用 Agent 的文字声明代替运行证据。
- 将未实际运行的测试标记为 PASS。
- 为获得漂亮结果而修改性能统计数据。
- 自动接受有风险的截图差异。
- 隐瞒失败或环境阻断。

允许修改错误的测试，但必须通过独立证据证明原测试与已确认的业务合同不一致，并单独记录原因。

## 4.4 禁止无约束大规模重构

MiniMax 每次应优先解决一个独立问题。

没有明确批准，不允许自行修改核心架构、大规模搬迁源码、调整公共 API、改变存储格式或删除大量历史文件。

涉及高风险架构修改时，必须停止相关自动修复并提交审查报告。

# 九、第五阶段：MiniMax 五小时额度监控与自动恢复

这是必须首先实现并验证的基础设施。

## 9.1 额度特点

我的 MiniMax 套餐周额度预计充足，但五小时窗口仍有限额。

希望 MiniMax 在额度不足前主动暂停，额度恢复后自动继续。

必须先核对 MiniMax 官方支持的额度查询机制，包括：

- CLI 查询。
- 官方额度 API。
- API Key 和订阅套餐绑定关系。
- 五小时窗口剩余额度。
- 下次恢复时间或滚动窗口信息。
- 短时间 RPM/TPM 限制。
- 查询接口不可用时的处理方式。

不要假设所有额度都以 Token 数或者百分比返回。

## 9.2 独立 Quota Watchdog

请设计可执行的 Node.js 额度守护程序。

不能只写“让 MiniMax 自己检查额度”。

推荐默认策略：

- 剩余额度高于 20%：正常执行。
- 剩余额度低于或等于 20%：停止派发新的大任务。
- 剩余额度低于或等于 10%：禁止新增模型调用并进入保护状态。
- 实际额度恢复后：验证状态并恢复执行。

阈值必须可配置，并考虑单次任务最大预期消耗。

若官方没有可靠的百分比，则使用官方实际字段以及历史调用消耗构建等价保护规则，并明确误差和不确定性。

## 9.3 暂停和恢复

额度不足时：

1. 阻止新任务派发。
2. 让已完成的原子步骤写入检查点。
3. 记录工作区及 Git 状态。
4. 保留必要的测试证据。
5. 不强杀未知进程。
6. 不在未验证的半成品上进行 Git Commit。
7. 不在发布过程中随意中断导致状态不明。

恢复时：

1. 查询官方实际额度。
2. 确认额度满足安全阈值。
3. 读取持久化状态。
4. 核对 Git HEAD。
5. 核对 GitHub 远程提交。
6. 核对 npm 候选发布结果。
7. 检查原任务是否已经完成。
8. 只执行尚未完成的动作。

必须防止重复提交、重复发布和重复执行具有副作用的操作。

## 9.4 验收要求

必须通过故障注入证明：

- 额度快耗尽时可以暂停。
- 额度查询 API 不可用时可以安全处理。
- Agent 异常退出后能够恢复。
- 守护进程重启后能够恢复。
- 计算机重启后，在实际配置了持久化启动机制的前提下能够恢复。
- 恢复后没有重复 Git Commit。
- 恢复后没有重复 npm 发布。
- 测试证据和任务状态不会丢失。

不能仅写恢复逻辑而不运行测试。

# 十、第六阶段：冻结当前版本与 GitHub 远程保护

## 10.1 冻结基准

在开始任何自动修复之前：

1. 检查本地 Git 状态。
2. 检查当前分支。
3. 读取完整 HEAD SHA。
4. 对比远程 main。
5. 检查未提交修改。
6. 建立基准记录。
7. 创建基准 Tag。
8. 创建独立 QA 修复分支。
9. 将基准 Tag 和 QA 分支推送到 GitHub。
10. 核对远程 SHA。

建议：

- 稳定分支：`main`
- QA 修复分支：`qa/continuous-repair-20261020`
- 基准 Tag：`qa-baseline-20261020`

基准 Tag 不得使用会触发正式 npm 发布的 `v*` 命名。

如果本地与远程不同或存在未提交修改，必须保留原有内容，通过安全的 worktree 或其他隔离策略开展测试，不能直接覆盖。

## 10.2 每修复一个 Bug 都必须远程提交

这是一项强制要求。

**不是只执行本地 git commit，而是每个独立 Bug 修复通过对应测试后必须 push 到 GitHub QA 分支。**

每个 Bug 必须有唯一编号：

`QA-001`、`QA-002`、`QA-003`……

流程：

1. 发现问题。
2. 稳定复现。
3. 保存修复前证据。
4. 编写失败回归测试。
5. 分析根因。
6. 最小范围修改。
7. 运行测试。
8. 审查差异。
9. 创建 Git Commit。
10. 推送远程 QA 分支。
11. 读取远程 SHA 确认推送成功。
12. 检查 GitHub CI。
13. 更新 Bug 状态。
14. 进入下一问题。

提交示例：

`fix(QA-001): repair project import state`

禁止：

- 直接推送 main。
- 强制推送覆盖历史。
- 修改无关文件。
- 将凭据提交到 Git。
- 一次混合多个无关 Bug。
- 测试失败仍标记任务完成。

GitHub CI 失败必须保留错误证据并继续修复，不得隐瞒。

## 10.3 远程回滚

所有修复必须能够回退。

对于已经推送的提交，优先使用 `git revert` 或隔离分支上的受控修复提交。

禁止通过强制推送来抹除已有 QA 修复历史。
