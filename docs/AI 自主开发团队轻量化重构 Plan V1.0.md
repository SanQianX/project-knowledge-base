# AI 自主开发团队轻量化重构 Plan V1.0

**项目：** project-knowledge-base / ai-coding-workflow
**执行模型：** GLM
**执行方式：** Plan → Implement → Verify → Review
**实施里程碑：** M0 → M1 → M2
**优先级：** 真实开发效率 ＞ 功能数量 ＞ UI 完整程度
**实施状态：** 待 GLM 执行

------

# 1. 目标、原则与开发边界

## 1.1 核心目标

将现有 `ai-coding-workflow` 从固定流程的 AI 团队任务管理工具，逐步调整为真正能够辅助 Claude Code / Codex 开发的轻量级自主 Agent 团队。

最终用户只需在已接入知识库的客户端中输入：

**Claude Code：**

```
/project-knowledge:pk-team 修复 XXX 功能，完成测试和独立 Review
```

**Codex：**

```
$pk-team 修复 XXX 功能，完成测试和独立 Review
```

上述是目标使用方式。执行前必须验证两端的插件发现、Skill 调用和 MCP 连通性；不允许仅凭仓库存在 Skill 文件就宣称命令可用。

启动后应能够：

1. 识别当前项目和开发会话。
2. 自动检索相关项目知识与长期记忆。
3. 使用当前 Claude Code 或 Codex 执行正常开发。
4. 开发完成后，通过编排器启动独立 Reviewer。
5. 自动运行真实质量检查并收集证据。
6. 将 Review 问题返回当前 Agent 整改。
7. 整改后重新检查和 Review。
8. 所有必要验收项通过后交付结果。
9. 对复杂任务，可选启用 GLM Leader 规划和分工。

**首期成功的标志：用户不必手动切换 Claude Code 与 Codex，不必反复复制 Review 提示词，也不必自己维护多个 Agent 的执行顺序。**

## 1.2 已确定的架构决策

- Leader 独立配置，默认推荐 GLM。
- 每个 Worker 独立配置执行器。
- Claude Code、Codex、Workbench 都是可选执行后端。
- Workbench 不承担团队编排业务。
- 编排控制放在 `ai-coding-workflow`。
- 引入 LangGraph JS，作为可替换的编排实现。
- 长期记忆复用现有 Knowledge Engine。
- Event Bridge 保留原生客户端事件采集职责。
- 不建立第二套团队任务数据库或长期记忆数据库。
- 任务成功必须由服务端根据真实证据裁决。

## 1.3 必须遵守的开发纪律

**优先复用现有代码。**

- 首先读取仓库真实实现和 AGENTS.md。
- 不因为本计划提到新接口，就直接创建同名新模块。
- 如现有实现已经满足要求，只补测试和接口接线。
- 不复制 Workbench 的模型驱动、Profile 和会话管理实现。
- 不复制 Knowledge Engine 的记忆存储和检索实现。
- 不重写 Event Bridge。
- 不新增不必要的工作流编辑器、Agent 市场、聊天系统或任务中心。
- 任何删除必须先验证无真实调用方，并提供迁移或兼容方式。
- 禁止修改真实用户的数据目录。
- 禁止自动发布 npm、推送远程、部署软件。
- 所有测试使用隔离仓库、数据目录、端口和临时 Git 工作树。
- Windows 是必须验证的目标运行平台。

## 1.4 本计划明确不做

M0–M2 范围内不开发：

- 拖拽式工作流设计器。
- 无限层级的 Agent 团队。
- 多 Agent 大规模并行编码。
- 通用 Agent 插件市场。
- 完整的任务管理平台。
- 跨夜额度恢复系统。
- 自动部署和自动发布。
- 新的向量数据库或长期记忆服务。
- 跨项目复杂资源调度。
- 不必要的系统首页和日报页面。

这些功能只有在 M0–M2 的真实效率测试证明有价值后，才允许重新进入规划。

# 2. 目标系统架构

```
                  用户开发入口
          Claude Code / Codex / UI
                      |
               pk-team Skill
                      |
                MCP Adapter
                      |
              ai-coding-workflow
                      |
       +--------------+---------------+
       |                              |
  Task / Team Core              Orchestrator
  业务数据与验收                  LangGraph JS
       |                              |
       |                        Context / Review
       |                        Rework / Leader
       |                              |
       +---------------+--------------+
                       |
                Runtime Adapter
                       |
            +----------+----------+
            |          |          |
       Claude Code    Codex    Workbench
            |          |          |
            +----------+----------+
                       |
                 执行结果与证据

          Knowledge Engine / Vector Hub
             项目知识与长期记忆
```

## 2.1 职责分离

**ai-coding-workflow**

持有 Team、Member、Task、Run、Review、验收结果和调度状态。所有业务完成状态由本模块裁决。

**LangGraph**

编排上下文获取、检查、Reviewer、结果判定和返工路由。M2 增加 Leader 规划节点。LangGraph 不直接写入业务主状态。

**Agent Runtime Adapter**

负责真实执行，不能只模拟 Agent 回复。

**Knowledge Engine**

负责长期记忆检索、成员记忆组合和权限校验。编排器仅获得授权的检索结果。

**MCP + pk-team**

负责让 Claude Code/Codex 中的当前 Agent 调用团队能力，接收 Review 结果并继续整改。

## 2.2 最重要的运行约定

首期采用：

**当前交互 Agent 负责开发，编排器负责独立审查和协作。**

原因：

- 用户无需改变当前开发工具。
- 不需要接管已经打开的原生会话。
- 不需要重新实现完整的编码 Agent。
- 能直接减少跨客户端手工操作。
- 失败后可以回到熟悉的 Claude Code/Codex 继续工作。

不能假定 MCP 服务能主动向任意正在运行的交互会话注入指令。

因此首期由 `pk-team` Skill 指导当前 Agent 在完成修改后主动调用团队 Review 接口，等待结构化结果，并执行后续整改。

以后只有在确实需要完全脱离当前会话运行时，才增加后台自主编码执行器。

## M0.2 修复 repoPath / 项目身份传递

### 当前问题

`project_workflow_request_review` 在 MCP 层没有完整暴露仓库定位能力，而服务端审查执行需要有效的仓库路径。

现有 `taskRepoPath()` 还会从 `sourceRefs.repoPath` 读取路径，但 `sourceRefs` 实际保存为数组。

需要修复：

1. MCP 接口的参数合同。
2. 当前仓库身份解析。
3. 任务和项目的关联。
4. 宿主到工作流模块的仓库引用传递。
5. 独立启动工作流模块时的合法路径处理。

### 推荐实现

由现有项目注册体系确定 `projectId` 对应的可信 Git 根目录。

任务只保存必要的仓库引用，不把任意客户端提交的路径直接当作可信命令执行目录。

对于独立模式，允许经过明确授权和根目录验证的仓库路径。

禁止默认使用 MCP 进程的 `process.cwd()` 代替用户项目目录。

### 必测用例

- 已登记项目正常解析。
- 不存在的项目明确报错。
- 仓库外目录被拒绝。
- 同名不同路径的仓库不会误绑定。
- Windows 路径正确处理。
- 有空格和中文字符的路径正确处理。
- 客户端漏传 `repoPath` 时，不错误选择安装目录。
- 测试和 Review 使用的是当前任务的实际仓库。

**验收标准：** 通过 Claude Code/Codex 的真实 MCP 入口能够对正确的 Git 仓库启动检查。

## M0.3 修复验收证据映射

### 当前问题

现有 `applyCheckReceipts()` 在所有检查通过时，可能将全部 `automated` 验收项标记为满足。

需要改为：

**每一项验收条件，只能被指定类型的有效证据满足。**

建议在现有验收模型上兼容增加：

- `requiredEvidence`
- `evidenceRefs`
- `acceptanceRevision`
- `snapshotId`
- `status`

不要强制旧任务立即转换为新格式。

示例：

| 验收条件     | 合格证据                       |
| ------------ | ------------------------------ |
| 代码规范检查 | ESLint 对应收据                |
| 单元测试     | 实际测试命令的退出码和结果     |
| 类型检查     | 对应类型检查收据               |
| E2E 测试     | 实际 E2E 执行结果              |
| 模型 Review  | 已验证执行身份的 Reviewer 结果 |
| 人工确认     | 经过授权的人工确认记录         |

质量检查不可自动满足“功能实现正确”之类没有对应检查器的验收项。

特别修复：

- 缺少检查工具时不能标记为通过。
- 检查异常不能标记为通过。
- 旧代码快照的结果不能自动满足新代码。
- 修改验收定义后旧证据不得继续生效。
- 模型 Review 不能由普通客户端随意写入 `satisfied` 冒充完成。
- 人工验收需要可核对的授权来源。
- 存在未解决阻塞项时不得交付。

### 代码快照修复

检查 `captureSnapshot()` 对已跟踪、修改、删除和未跟踪文件的处理。

必须保证实际参与交付的源代码不被快照遗漏。

对于未跟踪文件，要求明确纳入本次变更范围；若无法确认完整性，不得宣称完整快照检查通过。

检查运行前后应核对快照身份，防止执行期间文件改变导致过期证据被接受。

**验收标准：** ESLint 通过不能冒充单元测试、E2E 或模型 Review 通过。

# 4. M1 — LangGraph 与跨模型独立 Review

**目标：** 实现第一次真正能够减少人工操作的 Agent 协作。

M1 是本次计划最重要的阶段。

## M1.1 接入 LangGraph JS

### 技术选择

使用官方 LangGraph JS 的 `StateGraph` 实现最小编排图。

首期只需要：

- 节点执行。
- 条件路由。
- 执行状态。
- 必要的持久化检查点。
- 错误处理。

暂不使用复杂的 Supervisor 框架、大型 Agent 模板或额外长期记忆 Store。

### 依赖隔离

现有 `ai-coding-workflow` 要求 Node.js 标准库实现、零运行时 npm 依赖。

因此：

- 核心模块继续保留该约束。
- LangGraph 放到独立的可选编排运行组件。
- 可以先在 `ai-coding-workflow` 仓库内部建立独立 package，避免新开不必要的仓库。
- 独立组件拥有自己的依赖和锁文件。
- 核心模块通过受信协议访问编排组件。
- 不将 LangGraph 的依赖直接加入原核心服务。

GLM 在实现前必须检查官方最新兼容版本，并固定依赖版本。

### Checkpointer

使用 LangGraph 支持的持久化 Checkpointer。

优先验证本地 SQLite 实现，以便重启后读取图状态。由于 JavaScript SQLite 实现可能涉及原生依赖，必须预先验证 Node.js 22 和 Windows 的安装及打包情况。

不能使用纯内存 `MemorySaver` 冒充可恢复的正式持久化实现。

LangGraph 检查点只保存编排状态；真实业务任务和外部执行收据仍由 `ai-coding-workflow` 持有。

本阶段仅保证 Review 作业的状态可核对，不扩展为完整跨夜自主编码恢复系统。

## M1.2 实现最小 Review Graph

建议采用以下节点：

```
START
  |
  v
LoadContext
  |
  v
CaptureSnapshot
  |
  v
ExecuteChecks
  |
  v
IndependentReview
  |
  v
EvaluateReview
  |
  +---- PASS ----> DeliveryDecision
  |
  +---- FAIL ----> ReworkRequired
  |
  +---- ERROR ---> Blocked / Retryable
```

M1 期间，代码整改仍由当前交互中的 Claude Code/Codex 执行。

整改完成后再次提交 Review，LangGraph 根据新的快照执行下一轮图运行。

不要求 LangGraph 直接接管用户当前会话，也不要求一次图运行内部完成所有代码修改。

### 节点合同

**LoadContext**

输入：Task、projectId、memberId。

行为：从知识库获取相关的项目决策、设计约束和 Review 规范。

输出：受限的上下文引用和内容摘要。

**CaptureSnapshot**

输入：仓库引用、本次变更范围。

行为：创建可核验的代码快照身份，识别变更文件。

输出：snapshotId、HEAD、变更文件清单。

**ExecuteChecks**

输入：snapshotId、检查策略。

行为：运行真实命令，记录退出码、完整性及执行日志。

输出：程序检查收据。

**IndependentReview**

输入：代码变更、验收要求、程序检查结果和相关知识。

行为：使用独立 Reviewer Agent 进行只读审查。

输出：结构化 ReviewResult。

**EvaluateReview**

行为：验证 Review 结果是否来自预期执行器、是否属于当前快照、程序检查是否完整。

不能仅凭模型回复“没有问题”就自动宣称所有验收通过。

## M1.3 实现 Claude Code / Codex Reviewer Adapter

只开发两个必要适配器：

- `ClaudeCodeReviewAdapter`
- `CodexReviewAdapter`

建议先实现 Codex Reviewer，验证成功后接入 Claude Code Reviewer。

原因是可减少同时排查两个 CLI 的复杂度。

### 执行要求

- 使用官方支持的非交互 CLI。
- 使用独立会话，不复用开发 Agent 的上下文作为审查结论。
- Reviewer 默认只读。
- 不允许 Reviewer 修改开发仓库。
- 使用参数数组启动进程，避免 Shell 字符串拼接。
- 设置超时、退出状态和输出大小上限。
- 不把凭据、环境变量秘密写入 Review 日志。
- 检查可执行文件和功能是否真实存在。
- 结构化输出经 Schema 校验后才能入库。
- 失败必须返回可诊断错误，不允许用预设的成功 JSON 替代。

### ReviewResult 结构

至少包含：

```
{
  "taskId": "task_x",
  "snapshotId": "snap_x",
  "reviewerMemberId": "member_x",
  "runtime": "codex",
  "status": "completed",
  "findings": [
    {
      "severity": "high",
      "file": "src/example.js",
      "line": 42,
      "category": "logic",
      "description": "发现的具体问题",
      "evidence": "支持判断的实际证据",
      "suggestion": "建议的修复方向"
    }
  ],
  "summary": "本次审查总结"
}
```

实际 Schema 需包括执行来源、Review ID、模型输出校验结果、时间和错误分类。

模型输出是审查意见，不天然等于已经证实的程序事实。

### 跨模型验证

必须真实完成：

**用例 A**

```
Codex 开发
   ↓
Claude Code 独立 Review
```

**用例 B**

```
Claude Code 开发
   ↓
Codex 独立 Review
```

如果某一执行器未配置、认证失效或额度不足，应诚实返回不可用状态；不擅自切换到其他收费模型。

## M1.4 接入长期记忆

直接复用现有知识库。

需要建立一个轻量 `MemoryProvider` Adapter，而不是新建记忆系统。

### 检索要求

1. 根据当前仓库确定 projectId。
2. 验证请求成员身份和记忆作用域。
3. 获取与代码变更、任务验收有关的少量高相关知识。
4. 尽量使用已有搜索工具和成员记忆组合。
5. 记录所引用知识的 ID 和版本。
6. 检索结果进入 Reviewer 上下文，但不能扩大工具权限。

### Token 限制

首期实行有界检索：

- 默认最多选择 5–8 条高相关记录。
- 优先读取摘要，必要时再获取正文。
- 使用可配置的 Token 预算。
- 不把全项目知识库注入每个 Agent。
- 已经通过上下文提供的信息不要重复查询。
- 同一快照的相同检索可短期复用。

该数量是初始建议值，GLM 应根据真实上下文质量和成本测试调整。

### 本期不做

- 自动将每轮聊天写成长期记忆。
- 独立 Agent 记忆总结服务。
- 再建设向量数据库。
- 新的记忆可视化管理页面。

已有长期记忆仍由 Knowledge Engine 管理。

## M1.5 对接当前 Claude Code / Codex 会话

这是 M1 必须解决的重点。

不能仅仅在服务器后台完成一个 Review，而让当前开发 Agent 不知道结果。

推荐采用：

**Skill + MCP 主动等待 Review 结果。**

流程：

```
当前 Agent 开发完成
       |
       v
project_workflow_request_review
       |
       v
返回 ReviewJobId
       |
       v
等待 / 查询审查结果
       |
       v
获得结构化 findings
       |
       v
当前 Agent 修复问题
       |
       v
重新 request_review
```

保留已有 `project_workflow_request_review` 和 `project_workflow_review_result` 的兼容语义。

可以增加一个有界等待工具，例如：

`project_workflow_wait_review`

用于减少 Agent 反复轮询和无意义 Token 消耗。

要求：

- 长时间 Review 不阻塞 MCP 请求直到超时。
- 作业状态有真实持久化记录。
- 同一 taskId + snapshotId + Review 策略不会重复产生无意义的审查执行。
- 结果返回到当前调用链，由当前 Agent 根据 Skill 规则继续整改。
- 当前会话已经结束时，保留可恢复的任务记录，不伪造“已自动注入会话”。

## M1.6 自动整改与复查规则

首期只实现受控循环。

默认策略：

- Reviewer 发现有效问题 → 返回当前开发 Agent。
- 开发 Agent 整改。
- 重新检查当前代码快照。
- 最多两轮自动整改复查。
- 超过上限 → 标记需要人工介入。
- 出现测试基础设施故障 → 返回环境问题，而不是盲目修改代码。
- 若 Review 与检查结果冲突，保留证据并要求进一步验证。
- 只对当前任务的变更范围进行自动整改。

没有具体文件、证据或可复现依据的 Review 建议，不得自动变成必须整改的高优先级问题。

## M1.7 LangGraph 的真实价值验收

LangGraph 必须实际参与节点执行和条件路由，不允许只是安装依赖或展示流程图。

真实验收：

- 检查通过时进入交付判断分支。
- 检查失败时进入整改分支。
- Reviewer 返回问题后，当前 Agent 能获得结果。
- 改动代码后旧 Snapshot 的结果失效。
- 重复调用同一 Review 不重复派发。
- 重启可恢复已持久化的 Review 作业状态。
- 无法确认外部执行结果时进入待核对状态。
- 主模块不需要直接依赖 LangGraph npm 包。

**M1 完成条件：一次用户任务能在 Claude Code/Codex 中自动完成跨模型独立审查、整改和复查，无需用户手动切换客户端。**

# 5. M2 — GLM Leader 自主分工

**目标：** 在 M1 稳定的基础上，为复杂任务增加智能规划和成员选择。

M2 不要求马上支持多个 Agent 同时写代码。

## M2.1 创建可独立配置的 Leader

保留原有团队成员数据和 ID。

兼容扩展：

- Leader 成员身份。
- `leaderMemberId` 引用。
- Leader Provider 与模型引用。
- Leader 行为规范。
- Leader 记忆组合。
- 预算与权限配置。

Leader 默认推荐 GLM，但不硬编码 GLM 为唯一选项。

Leader Provider 可以通过已有 Workbench 接口或独立、受信的模型 Provider 实现。若使用 Workbench，应是可选后端，不使普通 Codex/Claude Code 团队任务依赖 Workbench 启动。

尚未配置 Leader 时，M1 能力必须保持可用。

## M2.2 简单任务与复杂任务分流

不要每个任务都启动 Leader。

增加轻量任务复杂度判断，默认采用程序规则；不清楚的任务再询问 Leader。

建议分类：

**Simple**

单点修复、明确的局部修改、少量独立代码变动。

执行：当前 Agent 开发，M1 自动审查。

**Complex**

跨模块改造、多个独立子任务、复杂依赖、多种验收要求。

执行：GLM Leader 规划，选择 Worker，生成有界任务计划。

规则应可调整，不依赖硬编码的绝对文件数量判定复杂度。

用户显式要求使用 Leader 时，应在授权范围内允许强制启用。

## M2.3 Leader 输出合同

Leader 不输出自由格式的无限任务计划，而输出可验证 JSON。

建议字段：

```
{
  "goal": "实现当前任务",
  "complexity": "complex",
  "requiresTeam": true,
  "workItems": [
    {
      "id": "work-1",
      "goal": "分析和实现模块 A",
      "role": "developer",
      "dependencies": [],
      "acceptance": [
        "对应功能测试通过"
      ]
    },
    {
      "id": "work-2",
      "goal": "独立代码审查",
      "role": "reviewer",
      "dependencies": ["work-1"],
      "acceptance": [
        "审查结果已记录"
      ]
    }
  ]
}
```

系统负责校验：

- ID 是否唯一。
- 依赖是否存在。
- 依赖图是否有环。
- 成员是否启用。
- 执行器是否可用。
- 工具权限是否允许。
- 工作项数量是否超限。
- 预算是否满足。
- 是否要求未经授权的外部操作。

不能将 Leader 输出直接解释为可以执行的系统命令。

## M2.4 基于能力选择 Worker

成员能够独立配置：

- 执行器引用。
- 模型引用。
- 职责。
- 记忆组合。
- 允许的工具。
- 执行权限。

Leader 根据任务需求选择成员，但最终由程序校验是否可执行。

M2 首期允许串行委派：

```
Leader 规划
    ↓
Developer 执行
    ↓
Tester / Check
    ↓
Reviewer 审查
    ↓
Leader 决定是否需要重新规划
```

真正的多 Agent 并行写入、自动分支合并和动态团队扩容不在本期。

## M2.5 Leader 失败与降级

需要处理：

- GLM Provider 未配置。
- GLM 返回非法 JSON。
- 计划无法通过 DAG 校验。
- Leader 推荐的成员不可用。
- 预算不足。
- Leader 对同一问题反复规划而没有进展。

策略：

- 结构化输出校验失败允许一次有界修正。
- 仍失败则返回明确错误。
- 可以保留 M1 的单 Agent 模式作为用户主动选择的降级选项。
- 未经用户授权不能擅自切换到收费 Provider。
- Leader 不得修改已通过验收的事实证据。
- 重规划必须保留旧版本与变更原因。

## M2.6 实际效率验收

选取一个涉及两个模块的真实开发需求。

验证：

1. GLM Leader 读取项目知识。
2. 生成合理的有界工作项。
3. 根据成员配置委派。
4. 通过已支持的执行器真实完成工作。
5. 自动进入 M1 Review。
6. 收到问题后决定返工或重新规划。
7. 最终交付证据完整。

同时执行一个简单任务，确认没有无意义启动 Leader 或多个 Worker。

**M2 完成条件：复杂任务能减少用户手动拆解和分派，简单任务不会因为增加 Leader 而产生明显的不必要开销。**
