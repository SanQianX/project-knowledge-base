# Leader 与 GLM 的 Workbench 协作手册

## 角色与边界

Leader 负责知识检索、接口决策、任务派发、代码审查、独立复测和发布判断。GLM-5.3 负责限定范围内的实现与测试。最多两条独立执行线；修改相同文件、用户配置、运行实例、npm 安装和固定端口验收必须串行。

使用真实 Workbench，不以其他模型的原生子代理冒充 GLM。完全模式不是扩大授权：禁止自行清空数据、覆盖第三方配置、修改客户端信任记录或发布软件。

## 创建与检查会话

所有路径相对于运行中的知识库服务。服务地址应通过运行身份确认，不假设端口永远是 5757。

1. 读取项目投影，取得 Workbench 的 `contextId`；它不等于知识引擎的 `projectId`。
2. `POST /api/terminal/sessions`，明确设置以下参数；不要依赖 profile 的默认模型。

```json
{
  "context": {
    "contextId": "<Workbench 项目 ID>",
    "contextType": "project",
    "displayName": "<项目名称>",
    "workspaceRef": "<Workbench 项目 ID>"
  },
  "aiProfileId": "glm",
  "model": "glm-5.3",
  "agentId": "claude-code",
  "permissionMode": "bypassPermissions"
}
```

3. 核对回执的 `sessionId`、项目、`model`、`selectedModel` 和权限模式。模型不匹配不能继续派发。
4. 必要时使用 `PUT /api/terminal/sessions/<id>/permission-mode`，正文为 `{"mode":"bypassPermissions"}`；仅改变自己的任务会话。
5. 用户在“开始工作”选择对应项目后，可查看真实会话及工具执行。

## 任务合同

每批任务必须包含：任务编号、目标、真实仓库、已有知识引用、可改文件、禁止操作、失败复现、验收条件和交付格式。

可直接使用下面的短合同，替换具体路径与用例后派发：

```text
任务：修复一个已复现的问题，不扩展功能。
仓库：绝对路径；已有知识：文件与 commit 引用。
可改文件：明确清单。禁止：用户配置、真实数据、信任记录、发布和未授权提交。
复现：输入、期望、实际；先补失败测试，再修复。
编辑：先验证实际 apply_patch 入口；不可用时交付补丁正文。
测试：具体命令、Node 运行时、仓库外临时目录、绝对证据目录。
交付：根因、diff、首失败与复测结果、未完成项；完成后 idle 等待审查。
```

先解析实际 Git 根目录并检索已有知识，再对照当前源码。知识文件只读；不手写最终知识、staging 或引擎状态。源文件修改使用 `apply_patch`，不得混入用户已有改动。

派发前验证 GLM 的执行环境能调用补丁工具，不只写一句要求。Windows 可通过 `Get-Command apply_patch` 找到已安装入口，核对包装器实际指向的程序；用空补丁验证。若 GLM 没有可用入口，应交付补丁正文由 Leader 应用，而不是改用 `Write`、`Edit` 或 shell 写文件。发现违反方式时保留已有成果，显式中止并在同一会话纠正续跑，说明中止原因，不伪称运行超时。

`POST /api/terminal/sessions/<id>/input` 的正文为 `{"text":"<任务合同>"}`。保存 accepted 回执及 sessionId。返回忙碌或网络异常时，先读快照确认是否已接受，不盲目重发。相同批次只有一次有效派发。

## 跟踪、断线与长任务

- 执行中优先 `GET /api/terminal/sessions?contextId=<项目 ID>` 读取轻量状态，不反复加载数千条事件；终态或诊断时再用 `GET /api/terminal/sessions/<id>` 读取快照、权限与相关事件。
- `GET /api/terminal/sessions/<id>/events?after=<sequence>` 续接 SSE；保存已处理序号，重连不得重复消费。
- `GET /api/terminal/sessions/<id>/knowledge` 查看本次知识上下文。准备/输出日志不等于模型实际收到，原生送达仍需独立证据。
- 事件类型带驱动前缀，例如 `claude/tool-use`、`claude/result`、`claude/error`；不能只匹配无前缀的 `result`。
- 断线后先恢复快照，再续接事件；事件缺口不以空数组冒充完成。不得重复创建会话或发送已接受的任务。
- 不设置默认整轮工作期限。单次模型请求超时和后台维护的安全期限属于不同机制。
- 工作时间长不等于异常；检查进程、工具活动和错误。必要时显式 `POST /api/terminal/sessions/<id>/abort`，等待终态后再派发修订任务。不得因慢而自动停止健康工作。

Leader 只读取简洁检查点、相关 diff、测试结果和关键失败片段，不持续拉取完整思考流或整个事件历史。

当前 `0.13.2-rc.10` 已复现长历史截断后的游标重建缺陷，相关修复仍待验收。此版本的快照序号和合成事件时间不能作为全会话游标或实际运行耗时证据；优先读取轻量状态、真实审计时间及操作收据，不因 UI 没有新消息就重复派发任务。

## 审查与放行

GLM 交付根因、文件清单、先失败后成功的测试、Node 版本、证据路径和剩余风险，然后等待 Leader 审查。

`isError:false` 或会话 idle 只表示运行终态，不证明任务完成。若结果乱码、缺少可用 diff/测试/证据，先读实际文件和独立反例，标为无效交付；保留成果与原会话，在新 GLM-5.3 短上下文会话派发小批修正。不要据此提交、发布，也不能将乱码自行解释为成功。

Leader 独立复测关键链路。源码、npm 候选、正式安装和真实模型分别记录；端口在线、工具存在、替身测试或回答提到知识库都不能替代真实送达与索引证明。

审查通过后，Leader 仅提交相关代码和回归测试。观察提交的真实 Hook、维护、晋升与索引，再让下一批任务实际检索本次新增知识与 commit 引用。

安装、配置修复、重启和发布需单独的操作合同及受保护备份。候选只发布 `next`；正式包验收通过后才更新 `latest`。用户仍须亲自审查确实变化的原生 Hook，不写入或绕过信任。

临时工作树不得通过目录联接共用需要保留的 `node_modules` 后直接递归清理。本轮清理带联接的工作树后，主源码依赖目录为空；因此清理前必须枚举链接、核对真实目标并先安全解除联接本身，不能让递归操作越出临时目录。依赖恢复按原锁文件执行，保留首失败，不以恢复后的结果覆盖环境事故。
