# 给 Pro 的完整审查与 Codex 实施规划提示词

你现在担任 project-knowledge-base 项目的首席软件架构师、代码审查员和 Codex 实施规划师。

你的任务不是泛泛评价方案，也不是重新写一份抽象架构建议，而是基于指定 Git Commit 的真实源码和我提供的重构 Plan，产出一套可以直接交给 Codex 实施的、分阶段、可验证、可回滚、上下文高效的 Agent 开发流程。

## 一、本轮任务边界

本轮只进行以下工作：

1. 审查 GitHub 当前源码。
2. 审查现有重构 Plan 和日志 UI 验收原型。
3. 找出源码缺陷、Plan 冲突、遗漏、错误假设、迁移风险和架构问题。
4. 根据真实代码依赖，生成 Codex 可以直接执行的详细实施流程。
5. 生成一段最终可直接复制给 Codex 的实施提示词。

本轮禁止：

- 修改任何源码。
- 提交 Commit。
- 创建或更新 Pull Request。
- 推送分支或发布版本。
- 用未经源码验证的通用重构模板替代真实审查。

如果仓库、分支或附件确实无法读取，请准确说明缺失内容及其影响，不得假装已经审查。

## 二、必须准确理解的 Token 优化范围

本提示词中所说的“节省 Token”，只指本次开发改造过程中 Pro、Codex、主 Agent 和子 Agent 的上下文与模型调用成本。

它不指 project-knowledge-base 软件运行时的 Token 消耗。

因此，本轮不要因为“节省 Token”而新增以下项目运行时改造：

- 不要新增 Claude Code、Codex、OpenCode 或其他模型的运行时 Token Flow Audit。
- 不要为了省 Token 修改 Commit 分析提示词的业务内容。
- 不要新增运行时提示词缓存、Diff 分段、Token 用量统计、模型调用计费面板或 Token 日志。
- 不要为了省 Token 删除、合并或改变项目运行时的 AI 功能。
- 不要把开发 Agent 的上下文优化混入产品需求、数据 Schema、日志 Schema 或 UI。

原 Plan 已经要求删除项目初始化分析、模拟分析和手动初始化分析，并统一 Hook 与启动补查流程；这些仍需实施，因为它们是已经确认的产品与架构要求，不是本节新增的 Token 优化。

原 Plan 对同一 Commit 的幂等处理、失败恢复和串行推进也必须保留，因为它们属于数据正确性要求，不是新增的运行时 Token 优化。

开发过程的 Token 优化只能改变：

- Agent 如何分工。
- 每个 Agent 接收多少上下文。
- 代码和文档如何被检索、摘要及复用。
- 测试在什么阶段运行。
- Agent 如何交接结果。
- 主 Agent 如何整合共享模块。

开发过程 Token 降低只有在源码审查完整性、实现正确性、迁移安全性和测试覆盖均不下降时才算成功。

## 四、最终目标

我要把你的交付物和原 Plan 一起交给 Codex，让 Codex 在一个完整实施任务、一个开发分支或一个 PR 中完成全部范围，包括：

- 将现有软件框架升级为简单、职责清晰、低耦合、可测试、容易维护的轻量架构。
- 消除重复状态、重复路径规则、重复日志实现和重复业务逻辑。

“一次性完成”是指全部范围在同一个完整实施任务和同一个交付分支中闭环完成。

它不表示制造一个巨大补丁后才统一测试。实施内部必须按依赖分阶段，每个阶段都有验证门槛、清晰交接和失败处理。

## 五、不可被静默推翻的产品决策

以下属于已经确认的产品要求。

如果源码与这些要求不一致，应把源码列为待修改项；如果 Plan 的技术实现与源码冲突，可以修正技术方案，但不能静默改变这些产品决策。

1. 知识库分析只有两个公开触发入口：
   - Git post-commit Hook 实时通知。
   - 程序启动时补查遗漏 Commit。

2. 导入项目不执行初始化分析，不扫描整个项目推测需求。

3. Git Hook 必须满足：
   - 导入项目时自动安装并验证。
   - 删除项目时自动卸载。
   - 不提供手动安装、重新安装或卸载按钮和公开接口。
   - Hook 只通知主程序，不在 Hook 内执行分析。
   - 主程序未运行时不能影响 git commit。
   - 旧版本安装的错误 Hook 只自动迁移修复一次。
   - 不得直接覆盖用户或其他工具已有的 Hook。
   - 不再管理 CLAUDE.md。

4. Commit 知识必须尽量来自：
   - 唯一固定的 Commit 分析提示词。
   - 用户实际提出的 AI 开发需求。
   - 该 Commit 的真实 Diff。

5. 多项目可以并行分析；同一项目只能有一个补查流程，并按照 Commit 顺序串行处理。

6. projects.json 只保存项目索引，不保存高频运行状态。

7. 每个项目使用稳定的 projectId，并独立保存：
   - config.json
   - state.json
   - 按需创建的 requirements.jsonl

8. JSON 状态必须原子写入；修改项目索引必须有全局写入锁。

9. 用户流程必须保持：
   - 先在设置页面配置全局知识库根目录。
   - 再导入项目。
   - 导入时自动确定项目知识库子目录。
   - 最终绝对路径固定写入该项目 config.json。
   - 修改全局根目录只影响以后导入的项目，不迁移旧项目。

10. 用户知识库目录只保存 Markdown 等真实知识内容。

11. 用户主目录下的 .project-knowledge 只保存设置、项目元数据、日志、缓存、运行文件和派生索引。

12. 服务端、CLI、MCP、索引器和其他入口必须使用同一个路径解析模块。

13. LanceDB 使用唯一的内部路径，不能跟随用户知识库根目录移动。

14. 保持轻量本地软件架构。JSON、JSONL 和当前技术栈能够可靠实现时，不要为了所谓架构感引入微服务、额外数据库、消息队列或复杂框架。

15. AI API Key 允许明文保存在 settings.json。本次不要擅自改成系统凭据库；但日志、错误信息和导出文件必须脱敏，不能泄露密钥。

16. 日志继续使用轻量 JSONL，但必须形成真正的诊断体系：
   - trace、debug、info、warn、error、fatal 六级日志。
   - 使用 operationId、projectId、runId 和 Commit 串联业务链路。
   - 长期保存、轮转、容量保护和游标分页必须真实生效。
   - 生产 UI 只保留一套日志页面。
   - 原始 JSON 只能作为次级详情。
   - 改造后的 UI 以附件原型的目标部分和 Plan 内验收规格为准。

17. 迁移失败不得静默丢失用户项目、知识文件、Commit 位置、日志或 AI 配置。

在不修改源码的前提下，运行仓库已经存在且不会产生外部副作用的合理测试、构建、Lint、类型检查或静态检查。

要求：

## 八、不要盲从现有 Plan

Plan 表达的是产品意图和初步设计，不保证每个技术细节都正确。

必须主动找出：

- Plan 内部互相矛盾的要求。
- 与当前源码不匹配的文件、函数、接口和数据结构名称。
- 缺少定义的 Schema、状态转换和失败边界。
- 不完整的迁移、回滚、重试和异常恢复规则。
- 会导致重复分析、状态丢失、数据损坏或知识写错位置的边界情况。
- 为了“解耦”而产生的过度抽象。
- Plan 没有覆盖、但会阻止整体功能可靠运行的现有 Bug。

至少重点核实：

- 导入时创建知识库骨架与“禁止生成无意义空文件”是否冲突。
- requirements.jsonl 在多个 AI 会话同时写入时如何保证记录完整性。
- Markdown 写入、索引更新和 lastAnalyzedCommit 推进之间的失败边界。
- 单一 LanceDB 与多项目并行分析之间的写入调度。
- 项目目录归属如何识别，避免导入回滚或项目删除时误删用户数据。
- 迁移完成标记、Schema 版本、备份、失败重试和中断恢复。
- 日志达到容量上限后的确定性清理算法。
- 项目删除后历史日志和项目元数据之间的显示关系。
- 已有第三方 Hook、core.hooksPath、worktree 和 Windows 脚本场景。
- 同一项目被 Hook 和启动补查同时发现时的互斥和幂等边界。

发现问题时必须给出：

- 证据。
- 影响。
- 推荐修正。
- 对应测试。
- 是否改变产品行为。

不要只写“需要进一步考虑”。

如果问题不改变产品行为、数据兼容或技术路线，请采用最简单可靠的建议并清晰标注假设，不要把大量非阻塞选择重新抛给我。

## 九、Bug 审查范围

“修复所有可能存在的 Bug”不是可验证的完成标准。请转换为以下可执行标准：

- 对整个仓库进行一次横向静态审查和基线验证。
- 深入审查本次重构涉及的模块及完整调用链。
- 找出并纳入所有已经确认、能够提供源码证据或复现方法的相关 Bug。
- 无论位于哪个模块，只要可能造成数据丢失、知识写错、启动失败、程序崩溃或凭据泄露的高严重度问题，都必须纳入本次实施。
- 与本次改造无关、风险较低且无法安全顺带修复的问题，放入独立遗留清单，不得声称已经修复。
- 不能把没有证据的猜测标成已确认 Bug。

每个 Bug 至少记录：

- 唯一编号。
- 严重程度。
- 源码位置和证据。
- 触发条件或复现方式。
- 根因。
- 修复方法。
- 回归测试。
- 所属实施任务。

## 十、目标架构要求

目标架构必须从真实源码中推导，保持最小、清晰和轻量，不要预先套用微服务、DDD 或形式化多层框架。

目标至少满足：

- 每类数据只有一个事实来源。
- 路由层只处理协议、校验和结果映射。
- Commit 补查、项目生命周期、日志、路径、迁移和持久化各有明确职责。
- 文件读写通过统一 Store 或基础设施模块完成。
- 业务模块不直接整体覆盖 projects.json。
- 路径不能在不同模块中重复拼接。
- Logger 只有一个正式实现。
- 新旧运行路径不能长期并存。
- 依赖方向明确，避免循环依赖。
- 外部行为变化只来自 Plan 的明确要求或有证据的必要 Bug 修复。
- 单元测试、集成测试和端到端测试可以分别验证职责边界。

不要以新增文件数量作为解耦完成的证明。

每一个建议新增的模块都必须说明：

- 它拥有的数据或行为。
- 对外接口。
- 依赖对象。
- 调用者。
- 为什么不能合并到现有模块。
- 如何测试。

同时指出应继续保留和简化的现有模块，不要默认全部重写。

## 十一、开发 Agent 流程的 Token 与上下文效率

这一节只约束后续开发过程，不修改产品运行时。

### 11.1 总原则

生成实施计划时，采用“主 Agent 掌握全局事实，执行 Agent 只接收完成自身任务所需上下文”的方式。

要求：

- 主 Agent 负责读取全部审查报告、产品决策、共享 Schema、依赖图和最终 Diff。
- 子 Agent 只用于边界清晰、能够独立验证、不会争抢同一文件的任务。
- 不为了展示多 Agent 而强行拆分任务。
- 如果拆分带来的交接成本高于并行收益，应由主 Agent 串行完成。
- 同一模块的连续修复优先继续交给已经掌握上下文的 Agent，不要重复创建新 Agent。
- 降低 Token 不能降低证据、测试、迁移和最终审查标准。

### 11.2 建立一次、反复复用的共享事实

在 CODEX_IMPLEMENTATION_PLAN.md 中建立一份简洁的“共享事实与决策索引”，作为所有实施任务的共同事实来源，至少包含：

- 审查 Commit SHA。
- 不可变产品决策的编号。
- 真实入口和关键调用链。
- 共享 Schema。
- StorageLayout 和路径规则。
- 状态机及成功推进条件。
- 并发和锁规则。
- 迁移版本与失败恢复规则。
- 已确认 Bug 编号。
- 测试命令清单。
- 共享文件所有权。

后续任务通过编号引用这些事实，不要在每个任务中重复粘贴整段 Plan、整份审查报告或全部源码证据。

共享事实必须足以防止 Agent 误解，但应去重，不能把三个交付物做成内容几乎相同的副本。

### 11.3 每个任务使用最小充分 Context Packet

为每个实施任务定义一个 Context Packet，内容只包括：

- Task ID 和目标。
- 必须遵守的产品决策编号。
- 前置任务产物。
- 必须读取的文件、符号和相关测试。
- 允许修改的文件范围。
- 禁止修改的共享范围。
- 已确认 Bug 编号。
- 数据与接口契约。
- 本任务的验证命令和完成标准。

不要默认把以下内容全部发给每个执行 Agent：

- 完整对话历史。
- 完整仓库。
- 完整原 Plan。
- 完整 PRO_REVIEW.md。
- 所有其他任务的代码和测试输出。

只有当某项任务确实跨越这些范围时，才扩充它的 Context Packet，并解释原因。

### 11.4 检索与阅读策略

实施计划必须要求 Codex：

- 先使用 rg、rg --files、符号检索或等价工具定位调用点，再读取相关文件。
- 独立的只读搜索可以并行。
- 有依赖关系的搜索按结果串行推进。
- 对大型文件先读取相关函数和邻近上下文；只有理解模块全局状态确有必要时才阅读全文。
- 已经由主 Agent 验证并且文件未变化的事实，后续 Agent 通过事实索引引用，不重复全仓库审查。
- 当共享文件发生修改时，只使依赖该文件的相关事实失效，不要求所有 Agent 从头重读。
- 大量确定性搜索、去重、映射和测试结果整理优先交给脚本或工具完成，不用多个 Agent重复总结。

### 11.5 Agent 分工和文件所有权

CODEX_IMPLEMENTATION_PLAN.md 必须包含文件所有权表。

至少明确：

- 哪些只读审查任务可以并行。
- 哪些实现任务可以在互不重叠的文件范围内并行。
- 哪些共享模块必须串行。
- 哪些文件只能由主 Agent 或集成 Agent 修改。
- 每个测试文件由哪个任务负责，避免多人同时编辑。

不能让多个实现 Agent 同时修改：

- server.js。
- 共享设置 Schema。
- 公共路径模块。
- 项目索引 Store。
- 迁移入口。
- 同一个测试文件。
- 其他经审查确认的高冲突共享文件。

主 Agent 负责共享架构决策、Schema 冻结、冲突解决、server.js 最终整合、迁移入口和最终回归。

### 11.6 测试调度

为减少重复上下文和无效执行，同时保持质量，测试按以下层级安排：

- 审查阶段运行一次完整基线。
- 每个实现任务完成后，只运行与该任务直接相关的单元或集成测试。
- 修改共享 Schema、迁移、路径或主整合点后，运行相应的跨模块验证。
- 关键阶段门完成后运行一次受影响范围的回归。
- 所有任务整合完成后运行完整测试、构建、Lint、迁移测试和端到端冒烟测试。

不要每修改一个小函数就重复执行全部测试。

也不能为了节省 Token 跳过必要测试。若针对性测试暴露共享回归，应立即扩大验证范围。

对已记录的基线失败，不要让每个 Agent重复调查；指定一个责任任务处理或明确列为环境阻塞，并在最终回归时统一复核。

### 11.7 精简交接

每个 Agent 的交接只保留：

- 完成了什么。
- 修改了哪些文件和符号。
- 做出了哪些新决策。
- 运行了哪些测试及结果。
- 仍有哪些风险或阻塞。
- 哪些共享事实需要更新。
- 下一任务必须知道什么。

不要要求每个 Agent分别生成长篇审查报告、复述整个 Plan 或粘贴完整日志。

测试失败时保留失败命令、关键错误和定位结论；不粘贴与判断无关的大量输出。

### 11.8 进度和文档

- 只维护一份主任务清单和一份共享事实索引。
- 不为每个阶段创建内容重复的临时 Plan。
- 只在重大阶段完成、依赖变化或发现会改变计划的问题时更新状态。
- 不逐条复述普通工具调用。
- 使用需求 ID、Bug ID、Task ID 和测试 ID 交叉引用，减少重复文字。
- 阶段摘要应保持短小，但不能丢失未完成项、失败项和迁移风险。

### 11.9 Token 效率验收

Pro 必须在 CODEX_IMPLEMENTATION_PLAN.md 中增加“开发上下文效率”章节，证明计划已经做到：

1. 每项需求只在共享事实中完整定义一次，其他位置主要通过 ID 引用。
2. 每个执行 Agent 都有明确的最小充分 Context Packet。
3. 没有两个 Agent重复执行同一全仓库审查。
4. 没有多个 Agent同时修改共享高冲突文件。
5. 全量测试只安排在基线、必要阶段门和最终验收；任务内使用针对性测试。
6. 同一模块的后续修复尽量复用原 Agent 上下文。
7. 没有为了省 Token 省略源码证据、关键测试、迁移验证、UI 验证或最终 Diff 审查。
8. 不要求给出无法证明的精确 Token 数或“降低 50%”之类目标。
9. 如果环境能测量开发过程输入量，可以提供数据；否则使用文件行数、字节数、上下文包数量和重复读取次数作为代理指标，并明确标注为估算。
10. 这部分优化没有产生任何新的项目运行时 Token 需求。

## 十二、必须交付的三个结果
