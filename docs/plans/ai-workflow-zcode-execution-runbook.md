# Zcode GLM 工作流模块执行与回归验收手册

修订日期：2026-11-15。读者：实施本需求的 Zcode／GLM、复核者和项目所有者。状态：实施规范，本文列出的功能、测试和发布均未因文档存在而完成。

本文与[主开发计划](ai-team-development-test-plan.md)共同构成执行输入。主计划提供 R1–R17、T01–T32、代码审查和领域约束；本文提供具体产品操作、工作包、RG 回归、U 用户验收、I 独立模块验收及 G 闸门。首次执行读完后从 W0 开始；已有进度则核对源码/收据，从实际断点继续，不清空记录或重新实施已验证阶段。用户无需逐阶段再次授权“继续”。

## 1. 执行合同和固定决策

### 1.1 本次必须实现

- 新增一个独立工作流模块，私有源码仓库、公开 npm 运行包、独立服务和数据目录；保留现有四模块，主产品变为五模块。
- AI 团队页面及团队、成员、跨项目任务、流程、程序质量检查、Review 编排、交付判定、日报提醒都由工作流模块拥有。
- Workbench 继续提供 Profile、凭据、driver、会话和受信执行；knowledge-engine 管理记忆正文、组合和成员绑定；Event Bridge 提供原生采集；vector-hub 提供派生检索。
- 六页主导航新增“AI 团队”，一个默认团队跨项目复用。开发成员跟随原生 Claude Code／Codex；Review 成员后台按需执行。
- 默认自动记录已关联任务，在交付检查点自动检查和 Review；当前有效证据满足后自动完成，需要人工判断的验收项保留待确认。
- JS/TS、C++ clang-tidy 和 Go 分别通过真实工具验收；完成 npm 和 Windows 安装包的受审发布流程。

### 1.2 不允许自行改变

不得把团队或任务主数据塞入 Workbench/shell，不复制 engine 记忆正文，不修改 `memberMemoryIds` 的现有含义，不引入第二套任务主库，不改成 Paperclip 等通用平台，不增加自由编排画布、组织树、市场、飞书机器人或自动删代码。

不得通过删回归、降低断言、扩大 ignore、修改阈值、篡改快照、只跑快乐路径或把真实测试换成替身来通过验收。允许修改与用户确认的新行为冲突的旧测试，例如五页改六页，但要保留原测试目的和新的正反例。

用户尚未给出的函数行数、复杂度、重复率阈值不由 GLM 自行定成强制标准。已有项目 Git 配置优先；缺配置时展示具体建议和适用范围，由用户应用到项目后成为该项目策略。合成测试夹具使用固定的专用阈值以制造正反例，不把测试阈值写入真实项目。必需检查缺配置时明确待配置，不悄悄当作无需检查或通过。

所有仓在 `main` 开发，保留未提交工作；新工作流源码不复制回主仓，不编辑安装树当作源码。新增依赖、存储或协议如需超出本文，记录具体失败证据和最小变更，交回范围决定；不能以“优化架构”为由自行扩张。

### 1.3 授权和停止边界

执行本轮“文档落盘”只允许改本文、主计划和价值计划，不执行 W0–W8。未来用户明确要求“按计划开发”时连续推进全部 W0–W8；已完成阶段先核验证据后接续。没有发布授权时完成候选构建、测试和所有可准备的证据，再保留具体发布待办。正式发布按既有工作流的人类验收合同，不伪造 `reviewer` 或人工声明。

无论何种开发/测试/发布授权，未经单独明确要求都不能停止、替换或升级用户日常安装。生命周期测试隔离失败，相关测试记 BLOCKED，不尝试清理真实服务。

### 1.4 连续执行和断点恢复

W0–W8 属于一个整体交付，阶段报告是中间进展。完成 W0–W2、建好页面、形成初版或通过部分测试都不是停止点。不得在这些位置结束并询问“是否继续”，也不得把用户要求的全量任务改为只做当前里程碑。

每次完成一个可验收步骤后执行下列循环，直到整体交付或确实无法推进：

1. 核对当前代码/包/环境和对应收据，更新真实进度；阶段条件通过后把下一阶段置 READY。
2. 选取下一项前置满足的工作，继续修改和测试。阶段报告之后仍在同一运行中继续执行，不能只留下“下一步计划”就停。
3. 测试失败进入修复和复测；保存失败历史，不删除用例、不跳 Gate，不把失败误称外部阻塞。
4. 某项需要外部凭据、真实人工验收、权限或环境时，记录具体 BLOCKED 条件、缺什么及证据；继续不依赖它的功能、回归、文档、构建和候选准备。没有任何可推进工作时才把阻塞交回用户，不每完成阶段就重新索要确认。
5. 全部已授权工作和必需验证通过后，生成整体交付报告；发布仍有真实人工条件未满足时只能报告开发/验收的实际级别，不能说 W8/G7 已完成。

在 `.local-test-data/ai-workflow/<runId>/execution-progress.json` 原子保存可恢复进度：runId、各仓源版本/工作树快照、每个 W 的状态及证据、当前 Gate、失败/阻塞列表、下一项可执行动作和续跑入口。该文件是索引，不替代原始测试收据。W 状态采用 NOT_STARTED/IN_PROGRESS/PASSED/BLOCKED，不靠日志标题推断通过。

用户已报告当前执行在 W0–W2 后停下：恢复时先读取已有工作流源码仓、主仓提交、测试产物和进度文件，复核这些阶段实际实现与证据。证据可复用则直接推进 W3；只有缺失或被当前变更失效的内容才补验/修复。不能凭用户一句“执行到”把三阶段全部代标通过，也不能默认从零重来。

如执行平台强制中断、上下文耗尽或服务重启，尽可能先写上述进度、未完成列表和可复制续跑指令；强制中断不等于任务完成。新运行从最后可验证的断点恢复。提示词不能替执行平台消除硬性运行限制，不允许承诺跨平台限制永不暂停。

## 2. 名称、边界和最低接口合同

### 2.1 固定名称和运行方式

| 项目 | 固定值 |
| --- | --- |
| 源码仓库/本地目录 | 私有 `ai-coding-workflow`；`D:\SanQian.Xu\ai-coding-workflow` |
| npm 包/首版 | `@sanqianx/ai-coding-workflow@0.1.0`；发布前核对名称归属和版本占用 |
| 服务标识/默认端口 | `workflow`；首选 5810，走已有动态端口解析，禁止抢占监听者 |
| 运行时 | Node ≥22、CommonJS、标准库服务端、原生 HTML/CSS/JS 页面 |
| CLI | `ai-coding-workflow serve --data <独立目录> --host 127.0.0.1 --port <端口>` |
| 独立数据 | 主安装 `<dataDir>/workflow/`；独立启动使用显式 `--data`，禁止复用 Workbench 状态目录 |
| 目录 | `src/` 业务与 HTTP，`ui/` 模块页面，`test/` 必需测试，`docs/` 契约 |
| 独立 API | `/api/workflow/v1`；普通读写都由工作流模块处理 |
| shell 代理 | `/api/workflow/<rest>` → 工作流 `/api/workflow/v1/<rest>` |
| 页面代理 | `/workflow-ui/`，页面 `embed=1&apiBase=/api/workflow`；静态资源相对该入口解析 |

2026-11-15 只读 npm 查询中该工作流包公开元数据返回 404，核心 5.1.0 未发布；这不是远端仓库已创建或命名已保留的证明。W0 核对实际归属，存在同名未知内容时不覆盖。

包内不包含日志、测试数据、用户知识、模型凭据或临时 clone。源码仓库私有不使公开 npm 运行代码保密。新仓继承主仓的 main 开发、隔离测试、真实实例保护和不自动发布规则。

### 2.2 数据归属和依赖方向

工作流拥有 teamId/memberId/taskId、验收版本、会话绑定、代码快照、工具收据、Review 业务结果和提醒。Workbench 拥有 executionId/sessionId、模型配置和执行事实。engine 拥有记忆/组/绑定关系及生效集合。工作流 ID 不复用原生后台 taskRef、Workbench driver agentId 或模型名。

工作流独立消费 Bridge journal，先保存可重放 inbox/派生事实再 ACK，不能使用 engine 游标。文件状态采用主计划的原子写、单写者锁、revision/CAS 和 outbox；跨文件不声称事务原子。首版不引入数据库。队列、调度和程序检查留在工作流服务，耗时 CLI 使用子进程，不能阻塞 HTTP 主线程。

工作流请求后台 Review 时经 HTTP 使用 Workbench。工作流不可达时，Workbench 原生聊天保持可用；Workbench 不可达时，工作流已有任务仍可查询，新增模型执行排队或明确受阻。engine 向工作流的成员核验只读取身份，不回调上下文，避免循环调用。

### 2.3 必需 API 和调用结果

主计划第 11 节为完整接口族。最少需实现：

| 能力 | 模块内路由/工具 | 必须返回或遵守 |
| --- | --- | --- |
| 默认团队 | `GET/POST/PATCH /team` | 每 brain 一个默认团队，稳定 ID；重试不复制成员 |
| 成员 | `GET/POST /members`，`GET/PATCH /members/:id` | 职责、执行方式、配置状态、revision，禁止返回凭据 |
| 项目启用 | `GET/PUT /projects/:id/settings` | 是否启用、审查开关、项目检查配置及能力缺口 |
| 任务 | `GET/POST /workflow-tasks`，`GET/PATCH /workflow-tasks/:id` | 分页、阶段、业务/运行/观测状态，done 不可普通写入 |
| 关联与进展 | `POST /workflow-tasks/:id/session-bindings`，`POST .../checkpoints` | 经核验的会话区间、真实/候选区分、验收及代码版本 |
| 审查/验收 | `POST .../reviews`，`GET /review-runs/:id`，`POST .../acceptance-decisions` | 固定快照和检查集合，真实收据；失败/未知不能自动通过 |
| 总览/恢复 | `GET /workflow-overview`，`GET /workflow-changes?after=...` | 有界投影、revision、缺口/重连状态；不能失败显示零待办 |
| 成员核验 | 受信 `POST /internal/context-bindings/validate` | 当前 binding/member/project revision，失败不放宽成员读取 |
| 客户端工具 | `project_workflow_start/resume/status/checkpoint/request_review/review_result` | 调用工作流主库，完整 requestId；不生成第二套任务文件 |

所有管理写入有请求幂等 ID，更新有 expectedRevision；同 requestId 不同载荷/CAS 冲突返回 409。错误至少区分身份/范围失败、冲突、能力未支持、服务不可达和执行失败；客户端可展示操作性提示，不回显凭据或未脱敏供应商错误。列表 limit 上限 100，使用 cursor。不要把未知状态默认为成功或空结果。

默认团队创建只涉及持久化和接线，不运行模型。创建后跨模块关系尚未同步时显示 pending 并允许原 ID 重试，不能伪就绪。成员禁用优先阻止新运行及身份核验，身份投影更新失败也不允许凭旧缓存继续读取。

### 2.4 Workbench 执行适配必须证明的能力

先在 W0 记录现有能力，在 W1/W5 交付下述同一合同：优先复用现有受信执行路径；现有普通会话或委派无法满足时，仅新增受信 `POST /internal/executions` 及 `GET /internal/executions/:executionId`、按 requestId 对账入口，均位于 Workbench 当前版本化 API 下。

输入最少为服务拥有者 storeId、requestId、externalRunId、已登记 context/workspace 引用、profile/model 选择、受限任务输入及执行权限。接受结果持久化 executionId/sessionId 和接收事实。重复请求返回原结果；接收超时后先按 requestId 对账，不能无条件重发。进程崩溃无法证明未发送时返回 dispatch_unknown。不存在父会话时不能调用伪造父会话的 delegation 合同。

Review 首版使用能证明工具限制的现有 Claude driver 和可用 profile；原生开发仍支持 Claude/Codex。Workbench 必须把工作区指向冻结快照，配置可用的读取/搜索/报告工具限制，禁止对原仓写入和通用任意 shell。驱动无法证明只读限制时该执行能力为 unsupported，不用提示词承诺替代。质量 CLI 由工作流受控 runner 执行，模型只读取结果。

工作流包不静态依赖 Workbench npm 包的内部文件，不读取 credential 文件。新接口兼容旧宿主，不要求所有独立 Workbench 用户配置 engine 或工作流服务。

## 3. 用户页面和创建团队

### 3.1 导航和页面归属

主导航固定为：首页、AI 团队、长期记忆、项目、知识检索、活动记录。模块自带团队页面，shell 同源嵌入；嵌入时隐藏重复品牌和主导航，保持原主题、项目和可见性消息，校验 origin/source。独立打开模块仍可看完整团队页。

AI 团队页四个页签固定为任务、成员、工作流、工具与接入。默认全部项目，筛选状态独立于知识检索和长期记忆当前项目，不能悄悄漏掉其他项目。

首页增加跨项目任务摘要及“查看全部任务”；项目详情只展示该项目团队启用和任务摘要；活动记录对开发任务、审查、知识维护有明确类别。组合管理继续在长期记忆页，新增成员使用者列表和跳转。

### 3.2 空态和建队三步向导

无团队显示“创建你的 AI 开发团队”，主按钮“创建我的团队”。服务失败显示不可达与重试，不能用空团队占位。无项目时导入入口返回团队向导并保留草稿。

| 步骤 | 字段/默认值 | 保存和验证行为 |
| --- | --- | --- |
| 1 设置成员 | 团队名“我的开发团队”；开发成员、Review 成员；姓名/职责可改 | 开发成员执行方式为“跟随当前开发会话”；模型由原生客户端控制。Review 选择已有可用 profile/model，缺失提供配置入口并保留草稿 |
| 2 记忆和检查 | 每成员多选已有组合；按项目读取已有质量配置，查看工具可用性 | 引用记忆不复制正文。没有组合可以继续，显示未绑定。没有工具配置提供预览，点击“保存到项目”才写项目 Git 配置，不自动安装工具或修改 ignore |
| 3 项目与启用 | 多选已导入项目；默认自动记录、交付检查、实质代码 Review、站内提醒开启 | 默认关闭后台自主派发编码、自动删改、外部通知、全历史补跑；点击“创建并启用”后创建稳定记录，不立即调用模型 |

返回/取消不产生半成品运行。重试使用同创建 requestId。只要仍有必需模型/接线未就绪，就显示具体配置状态，不阻止用户查看已有任务。项目记忆和成员记忆分别列出来源，不将记忆绑定当作写代码或发布权限。

### 3.3 任务、成员和结果页

任务列表显示项目、任务标题、阶段、业务状态、运行情况、最近活动、阻塞、下一步和结果入口；可筛项目/状态/关键字。显示“已验证 2/4 项”，不生成无依据百分比。默认只列活跃/近期任务，归档可查。

任务详情四个页签：概览、进展、代码审查、验证证据。概览包含原需求/验收/下一步；进展链接原会话和检查点；审查分程序发现、模型意见、简化/删除候选及未知项；证据显示代码/规则/工具版本、命令、退出状态、完整性和过期状态。

按钮固定为“继续开发”“提交审查”“暂停自动审查”“归档任务”；仅人工验收项显示“确认验收项”。继续开发复制带 taskId 的短接续指令，不另建会话；发布前不承诺打开或接管任意外部客户端。

成员卡片显示职责、执行方式、配置状态、绑定组合数和参与任务。就绪不等于运行；无任务不显示持续工作动画。成员详情支持修改职责/模型引用、组合绑定、生效预览、历史和禁用。长期记忆组详情展示项目及成员使用者，共享编辑展示影响范围，解绑仅解除关系。

工作流页只提供固定步骤及项目适用性、必要检查和自动审查配置，不做自由画布。工具与接入展示各项目语言工具版本/配置/缺失项，以及各客户端真实握手、Hook 信任和最近成功事件。

### 3.4 产品文案与可用性

必须区分没有任务、未启用、未安装模块、正在同步、服务不可达、未运行检查、失败、证据过期和部分采集。错误可重试且不丢用户输入。键盘可完成向导和对话框，关闭后焦点返回触发控件；浅/深色和窄屏内容不被遮挡。用户流程不展示 journal/CAS/driver 等内部术语，只在可展开诊断中显示。

## 4. 原生开发工具中的用户流程

### 4.1 一次接入及准确入口

复用现有 project-knowledge 插件和 Bridge 安装路径，新增 `pk-team` 技能和工作流 MCP 工具。只安装一套采集，不另起重复捕获链。Claude 插件入口为 `/project-knowledge:pk-team`；Codex 通过技能选择器或 `$pk-team`，复制按钮使用该客户端实际注册的入口。

计划提供以下操作，不能在实现前称其已存在：

```text
Claude Code：
/project-knowledge:pk-team start 修复请求超时后的重复重试问题
/project-knowledge:pk-team resume <taskId>
/project-knowledge:pk-team status
/project-knowledge:pk-team review

Codex：
$pk-team start 修复请求超时后的重复重试问题
$pk-team resume <taskId>
$pk-team status
$pk-team review
```

接入诊断核验项目、客户端、插件版本、MCP 握手、Hook 加载/信任和测试事件。配置文件存在不等于可用。不得绕过信任、修改用户未选择的项目配置或把原生登录自动当作后台 Review 已认证。[Claude 技能](https://code.claude.com/docs/en/skills)、[Codex 技能](https://learn.chatgpt.com/docs/build-skills)、[Codex Hook](https://learn.chatgpt.com/docs/hooks)说明调用及信任形式；实际发布前按已安装客户端版本重新核对并做真实验收。

### 4.2 每日开发闭环

1. 用户显式 start 新需求，或网页建任务后复制启动指令；服务核对项目、请求原文来源和客户端会话，再创建/关联任务及开发成员，返回短任务合同和 taskId。
2. 用户继续正常编码；有意义的检查点自动更新，推断与事实分开。不要求每轮填状态，普通问答不建任务；隐式技能匹配只作便利，不承诺必触发。
3. 工作流技能在准备交付时提交当前任务检查点并请求审查；可配置的关联 commit 也触发。普通 Stop、idle、提交存在只更新运行事实，不直接完成任务。
4. 相同快照和策略请求合并；程序检查固定代码版本，必要模型 Review 读取同一版本。连续事件最多合并等待 10 秒，不能每次输入/保存都全仓检查。
5. 页面显示真实审查结果，客户端在下个受支持入口读取；不承诺后台结果能随时插入正在生成的回复。工作流不可用时原生开发可继续，观察状态显式降级。
6. 当前开发会话整改。Review 不写原仓，整改后生成新快照。自动复查最多两轮，仍失败保留阻塞、证据和下一步，不自行放宽规则。
7. 服务端核对当前验收 revision、快照、必需检查、Review 和人工项后自动交付。模型报告只是输入，不能直接写 done。人工项未满足显示待确认。
8. 新会话 resume 指定 taskId，取得目标、已确认决策、当前版本、未完成项和下一步，沿用任务不重复建卡。多项目各自隔离，同一会话切任务必须明确切段。

原生身份由现有 Hook 可核验会话事实和一次性关联凭据建立，凭据限定项目/客户端/期限，不能仅相信模型传来的 sessionId/memberId。不同会话的身份材料不可互用。`agent-delegation/unknown` 不当作 human 偏好证明。

### 6.3 正式 CI 与触发原则

当前主仓非发布 CI 的六个必需 job 是：

```text
Core / Node 22.x / Linux
Core / Node 24.x / Linux
Core (web runtime) / Windows
QA controller / Node 22.x / Linux
QA controller / Node 24.x / Linux
QA controller / Windows
```

全部保留。新增固定命名 `Workflow contract / Node 22.x / Linux`、`Workflow contract / Node 24.x / Linux`、`Workflow UI / Windows`；新模块自己也有 Windows/Linux CI。主仓新增 job 必须使用主仓锁定的运行包/构建候选，不能只跑一个离线伪模块。

同步更新 prepare/promote 代码中的必需 job 列表和守卫测试，使缺失、失败、跳过、取消、旧 SHA 或旧 run 的新 job 无法提升候选；不能只在 README 增加必需测试。真实模型/客户端和官方安装独立收据绑定相同候选；没有凭据时可完成离线 CI，但 G5/G6 保持未通过。

每个改动先跑相关 RG；里程碑/候选跑完整相关仓套件和根 canonical 回归。修复后重跑失败及影响范围，最后完整候选冻结后再跑所需全套。测试耗时长时改进隔离/调度，不用减少断言或缩小回归范围掩盖失败。

新用例只覆盖关键行为及失效风险；不用每个 getter/字段生成镜像测试。测试计数、覆盖率数字或截图张数不能单独作为功能通过标准。

### 7.1 公共前置和执行层次

建立可跟踪的合成 JS 项目 A、C++ 项目 B、Go 项目 C。可重复生成器进入 Git；数据、日志、安装 prefix、截图和 snapshot 存在忽略目录。A 包含冗余旧路径、unused 导出、动态 bin/HTML/hook 入口反例及有效功能；B 包含 compile database/宏/include/头文件、函数大小违规与合法函数；C 含复杂函数、unused、平台/build tags 差异。

业务数据通过 UI 或公开客户端工作流创建。允许启动 harness、准备合成仓库和测试 profile、注入网络/磁盘/进程故障；禁止直接写业务数据库把团队/任务置为成功。浏览器真实点击/输入和 API/进程收据共同断言，最后刷新或重启测试实例检验持久化。

执行层标记：L1 为真实前后端/浏览器和受控模型替身；L2 为真实 CLI/Claude/Codex/有界真实 Review；L3 为官方 npm/桌面产物安装。L1 PASS 不能填写为 L2/L3 PASS。测试模型替身仅用于可重复故障和协议验证。

### 8.2 模块发布和主包锁定

1. 在各源码仓冻结已审 SHA，相关完整 CI 通过，包内容和 integrity 已核验。
2. 新工作流实现与 Workbench 相同原则的 prepare→受审 tarball→publish-next，发布不可重新构建。只能发布正确 scoped 包，身份不匹配/缺文件/dirty tracked tree/错误 hash 必须拒绝。
3. Workbench 复用已有 prepare/publish-next。engine 使用现有 expected SHA/integrity 和 next 流程。Bridge 原稳定版路径会移动 latest，本次新增独立的 reviewed-next 模式，只发布一次已审包到 next，并测试 latest 不变。
4. 不为了交付主产品强行提升所有模块 latest；主包依赖精确公开版本，即使它处于 next 也能按精确版本安装。原四依赖保留，新包第五依赖不使用 `^` 或 `latest`。
5. 主包锁定实际公开 tarball/lockfile，生成五模块 runtime manifest；从官方 registry 在独立安装验证，不复用本地 npm link/源码覆盖。

新工作流 Trusted Publisher 绑定若尚不存在，先完成不发布的身份核验并报告需要账号所有者设置的具体项目，不创建长期 token 或扩大其他包权限。现有受支持身份/工作流与私有源码 provenance 策略保持一致，不能套用一条通用 publish 命令给所有模块。

### 8.3 核心 next 与正式提升

沿用主仓实际[发布工作流](../../.github/workflows/publish.yml)的 `stable-prepare → stable-publish-next → stable-promote`，普通稳定 tag 不是自动正式发布。原旧 runbook 中“打 tag 自动 latest”的描述在 W8 更新。[正式提升守卫](../../qa-autopilot/tools/stable-promote.cjs)是人工声明和防漂移合同的代码依据。

1. 全部候选所需 CI 在同一源 SHA 通过，更新后的必需 job 清单含新增工作流/页面测试。
2. stable-prepare 仅构建一次并记录源 SHA、tarball SHA256/SRI、文件清单和版本；独立审查该包。
3. stable-publish-next 下载同一 prepare run 的原字节，核对 reviewer 和预期 hash，不重打包、不移动 latest。
4. 从官方 registry 下载精确候选进行 U29/U30 及完整关键流程，收据绑定同一 integrity。
5. Windows 草稿安装包通过第 8.4 节真实安装验收后，才进入 stable-promote。
6. 现有代码要求真人提供 `official-next-install-ui-restart-passed` 及 reviewer；这是人工声明，不是模型测得事实。Zcode 不伪造，提供已完成证据后保留该最后待办。
7. 提升前重新核对 expected_current_latest/next/SRI，冲突停止并重新审查；已提升同一产物时只对账。核验官方 latest 的实际内容，不只看 Actions 绿灯。

授权/人工验收尚未具备时状态为 READY_FOR_RELEASE 或 WAITING_HUMAN_ACCEPTANCE，不宣称正式发布。不得因不想等待人工声明而改掉现有发布门禁。

### 8.4 Windows 草稿构建和公开

在现有手动桌面工作流增加明确的 build-draft 与 publish-reviewed 两阶段，默认只构建草稿：

1. 精确核心/桌面版本和依赖同步，固定源 SHA/tag。候选核心已在官方 next 可下载，五模块全部已公开且精确锁定。
2. 复用现有打包 wrapper，扩展精确工作流/engine/vector 模块输入与包审计，保留现有原生库、ASAR negative self-test 和真实 exe 验证。
3. 产出 Setup.exe、full.nupkg、RELEASES、SHA256 清单及构建收据；上传草稿 GitHub Release，不自动公开。
4. 在干净独立 Windows VM 从草稿资产下载核对 hash，U31 新装、U32 旧桌面合成数据升级、原生 Claude/Codex 和实际 exe 场景通过。不能在用户日常安装路径运行安装器。
5. 人工实际安装验收与自动化报告一起绑定该资产哈希。核心完成正式提升后，publish-reviewed 只公开同一组已审资产，不能重新构建或默默替换同名资产。
6. 验证公开下载哈希及 Release Notes。Windows 安装包在 GitHub Release 交付，本次不要求另外发布 desktop npm 包。

发布流程不动日常托盘/后台实例；“发布成功”和“用户当前已升级”是不同事实。

### 8.5 失败、回退和发布说明

next/安装包验收失败保留候选与原始报告，不移动 latest、不公开草稿，修复后用未占用版本。Registry 传播延迟按已有有界轮询对账，不重复发布；截止未就绪记 PENDING。正式回退不强推/覆盖已发布版本，迁移后新增数据不能靠直接还原旧备份丢弃，优先前向修复或离线差量迁移。

Release Notes 必含：建队步骤、项目启用、成员组合、两个客户端准确入口、自动审查/交付条件、工具链要求、迁移与限制、关闭新增功能及保留数据方式。外部发布授权不包含停止或替换日常实例。

| G7 正式发布 | 发布授权和真实人工声明具备，核心 latest 与已审版本匹配，同一 Windows 资产公开且下载核验成功 |

“功能开发并回归通过”至少需要 G0–G5；“候选验收通过”还需要 G6；“完整发布交付”需要 G7。每个阶段允许已完成部分，但不得把 BLOCKED/NOT_RUN/SKIPPED/PENDING 写成 PASS。真正不适用条目使用 N/A，说明适用性依据及批准范围，必需真实客户端/三语言/安装验收不能自行 N/A。

旧基线存在失败时保留修复前后对照，不能自动排除其发布影响；正式候选所需回归仍必须全部通过，或者形成用户明确缩小范围的新计划，不能由执行 Agent 自批豁免。修复后原先未变的证据只有在影响/版本合同允许时复用，整包重构建后官方安装证据必须重新绑定。

### 9.2 每项证据至少包含

```text
caseId / requirementIds / workPackage / gate / layer(L1,L2,L3)
status(PASS,FAIL,BLOCKED,NOT_RUN,N/A,PENDING)
sourceRepository / sourceSha / worktreeSnapshot / candidatePackageVersion
tarballIntegrity? / installerSha256? / policyHash / toolchainHash
testCommand / cwd / sanitizedEnvironmentProfile / startedAt / finishedAt / exitCode
teamId? / memberId? / taskId? / nativeSessionRef? / snapshotId? / reviewRunId?
expected / observed / assertionEvidence / rawLogRef / screenshotRefs
limitations / failureReason / retryHistory / protectedInstanceBeforeAfterRefs
```

命令日志和截图记录真实位置及摘要哈希，不保存秘钥、系统提示词或整段无关个人会话。截图与运行结果相互关联，失败后重试保留失败历史，不只保存最后一次绿色结果。

源码 SHA 不能证明未提交工作树的完整内容：开发中记录工作树快照；正式发布必须绑定已提交且由 CI 验证的源 SHA 及不可变包。公开包使用 registry SRI，安装包使用资产 SHA256。不同版本/规则/环境结果不能拼成同一版本全绿报告。

### 9.3 必须交付的文件和报告

可复用 canonical 测试、harness、fixture 生成器进入各自源码仓；不是把所有一次性探针复制为产品测试。当前主仓 `_site/_test/fixtures/*` 默认忽略，新固定 fixture 要有明确跟踪规则或改成已跟踪生成器。

运行报告存放现有忽略目录下的独立 runId 路径，建议主仓 `.local-test-data/ai-workflow/<runId>/`；不要向源码提交真实 data、浏览器 profile、截图、日志、临时 clone 或安装 prefix。

每里程碑维护 `requirements-matrix`（R→T/U/I/RG→证据）、`regression-results`、`e2e-results`、`protected-instance-report`、`source-and-package-manifest`、`open-items`；W8 增加官方安装/迁移/发布收据。格式可为 JSON＋简短 Markdown，但字段和状态遵守第 9.2 节。

### 9.4 每轮给用户的进度报告

此模板用于中间进展，不是阶段完成后结束当前执行的指令。报告之后自动继续下一项 READY 工作，只有第 1.4 节的整体完成或确实无可执行项条件才提交最终结果。

```text
本轮工作包及实际改变：
涉及仓库、源版本及未提交变更：
已通过的测试/Gate：caseIds、真实命令、退出码、证据路径
失败/未执行/受阻：具体条件、影响范围和下一步
原功能回归：已跑范围、尚缺范围、是否可进入下一 Gate
受保护实例：前后身份/健康及测试隔离结论
当前交付级别：代码已改 / G0–G5 / G6 / G7

```

不要报告未执行测试为“应该通过”。依赖、认证、VM 或外部权限缺失时完成不依赖它的工作，留下确切阻塞；不能用另一个测试替代后宣布整项完成。

## 10. 后续增量 D0 到 D3 版本与文档维护成员

### 10.1 与当前交付的关系

本节对应主计划第 15 节 DR01–DR08，是用户提出的“后面添加”的成员能力。当前 Zcode 继续完成 W0–W8，不重新开工、不加第六服务、不因本节等待 UI 重做或扩写当前发布范围。当前发布要求的使用/API 文档、调用示例、版本同步和 Release Notes 仍由开发任务负责；新增成员是自动化维护这些工作的后续增量。

只有明确启动该增量后才实施 D0–D3；按同样连续执行约定推进，不将它自动并入当前 Gate。尚未启动标 NOT_STARTED，不能以新增文档代称成员已创建。

### 10.2 用户操作和自动维护

在“AI 团队→成员→添加成员”中提供“版本与文档维护”模板，选择姓名、可用模型、已有记忆组合和项目。预览可写范围、已有规范和版本同步方式，默认不授予发布/分支清理/业务代码修改权限。

项目可开启“自动文档维护”，触发点为公开接口变化或发布准备；也可在任务中手动请求。用户看到文档差异、API 变化、示例真实执行结果、版本建议及兼容风险，能跳到具体补丁和 docsRunId。未授权写入显示草案，已授权项目可在单写者/hash 检查下自动写文档，再由检查与 Review 接纳，无需每行重复确认。

工作流模块保存成员和维护任务；Workbench 提供该成员的受限执行能力；engine 管记忆。模型输出文档补丁，实际写入由受控 applier 限定授权路径并校验当前 hash，不开放任意 shell 写源仓。示例运行放独立实例，不能因文档维护去请求或变更日常服务。

### 10.3 D0 到 D3 的步骤

| 阶段 | 必做内容 | 通过后继续的证据 |
| --- | --- | --- |
| D0 清点规范 | 在各项目登记当前 README/API/SDK/CLI/示例/CHANGELOG/版本入口和维护者，区分当前/历史/计划/内部；核对旧 SDK 安装号和 vendoring 候选 | 文档索引、适用版本和现有失败基线；无自动全仓重命名/删除 |
| D1 程序检查 | 复用 Workbench 现有 SDK/OpenAPI/版本校验；新工作流使用 OpenAPI JSON；新增 docs:check 和 docs:examples 入口 | 路由/参数/响应/示例/版本/链接正反例，实际公开包隔离调用；不只 regex 包含字段 |
| D2 成员与工具 | 现有成员生命周期加 release-docs 模板、触发/去重、范围工具、补丁 CAS、来源/记忆/结果 UI | 用户可添加/绑定/启用；没有任务不启动；写入越界和并发修改被拒绝 |
| D3 联动与验收 | API 改动→文档最小更新→示例验证→Review；版本计划→清单检查；按需纳入后续发布 CI | DR01–DR08、DT01–DT12，通过后更新交付报告；当前 W0–W8 的 Gate 不倒退/代替 |

`docs:check` 校验规范语法及实现合同、路径/锚点/权限分类、版本和敏感内容；`docs:examples` 在测试数据根和动态端点实际执行示例、核验成功/错误响应并清理本轮资源。现有 `sdk:check/release:verify` 继续运行，不用新入口取代原检查。engine 的零运行依赖约束保持，不为文档检测向其服务引入新解析库；所需成熟校验器在已有工具链或测试环境固定版本运行。

后续发布将适用 docs/examples job 纳入该发布流程的必需检查与守卫测试，缺失/跳过或旧产物收据不能放行；没有文档变更不等于必然 N/A，接口变化必须触发相关检查。

### 10.4 DT01 到 DT12 的验收

| ID | 场景/操作 | 必须观察到的结果 |
| --- | --- | --- |
| DT01 | UI 添加该成员、绑定组合、启用项目、刷新再禁用 | 稳定身份/关系保留，无任务不启动，禁用阻止新维护；不增新服务 |
| DT02 | 修改真实测试 API 必填参数/路径/响应，保留旧文档或规范 | 检查具体报告差异并失败；不能让模型直接把规范改到迎合实现缺陷 |
| DT03 | 示例有错误导入、参数或失效 endpoint，再修正 | 实际执行先失败后通过；链接可达/空退出码不能代替预期响应断言 |
| DT04 | 使用独立端口、生成本轮 project/session ID 及测试认证运行示例 | 只访问本轮服务；新装可复现，无写死真实端口/ID/密钥 |
| DT05 | 分别从官方包和源码测试服务执行关键 HTTP/JS/PowerShell 示例 | 包接口和适用版本一致，独立/代理 URL 正确，响应/错误和资源清理可证明 |
| DT06 | 人为造成 package/lock/plugin/OpenAPI info/清单的版本漂移 | 按该模块合同失败；不混同 API v1、OAS 格式和数据 schema，不拉所有模块同号 |
| DT07 | 提出稳定 API 不兼容及 0.x 变化、只有文档变动的发布建议 | 保留变更依据及当前政策；不自行覆盖版本、升级所有包或当 0.x 永远兼容 |
| DT08 | 合并/移动含引用的旧文档，保留有价值历史 | 引用/锚点映射正确，历史可找到，无大批无依据删除及重复规范 |
| DT09 | 文档或示例出现合成密钥/内部令牌，检查打包文件 | 检查拒绝敏感内容进入正文/日志/包；内部接口与普通调用边界明确 |
| DT10 | 生成补丁后用户并发改同文件，再应用旧补丁 | hash/revision 冲突，不覆盖用户修改；重新取当前内容再做最小补丁 |
| DT11 | 成员尝试改业务实现、AGENTS、质量规则、真实知识树或发布 tag | 写入/执行边界拒绝；engine 仍为知识单写者，原任务和回归保持有效 |
| DT12 | 完整走接口变更、文档/示例更新、隔离验证、Review、发布候选 | docsRunId 绑定同一源/契约/版本计划及收据；模型声称通过不能覆盖失败，未执行不能放行 |

后续验收层次与 RG/G 相同：先单元/合同和受控故障，再实际 API/示例，最后适用的正式包/发布候选。通过报告逐项列 DR→D→DT→原始证据；当前核心任务已通过的旧功能仍按影响范围回归，不删除原测试。
