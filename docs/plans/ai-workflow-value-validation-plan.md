# AI 开发工作流价值评估与试点计划

创建日期：2026 年 11 月 13 日。适用对象：继续在 Claude Code 或 Codex 中开发的项目所有者。

2026-11-15 更新：用户已确认独立工作流模块，AI 团队页面和业务随私有源码仓库的独立 npm 包交付，Workbench 只提供执行。实施以[主开发计划](ai-team-development-test-plan.md)和[Zcode 执行与回归验收手册](ai-workflow-zcode-execution-runbook.md)为准。本文保留收益对照、试验投入和停止扩张条件，不提供另一套架构。下文 P0/P1/P2 是价值试验编号，生产开发采用 W0–W8。

续跑要求：用户已明确要求完整交付，不在 W0–W2 后停下。本文的成本上限、样本观察和投入建议不得被执行 Agent 用作终止已授权 W0–W8 的理由。阶段通过后自动继续；五工作日收益观察不足列为交付后 PENDING，技术验收仍按真实测试闸门执行。范围缩减或停止现有需求由用户决定。

## 当前决策

用户已明确当前存在四项负担：同时开发多个项目和任务，难以知道各项工作进行到哪里；需要花精力确认 Agent 是否真正完成并有效验证；Agent 开发速度慢；AI 倾向于不断添加实现，项目的复杂度和冗余逐步增加。开发优先级据此调整为跨项目进度总览、交付与代码质量核验、慢速诊断，跨会话接续作为进度记录的复用场景。

跨项目进度、交付核验和按指定规则审查代码已有明确使用需求，值得进行有预算上限的验证。代码质量审查角色纳入 P1，职责包含识别可复用、可简化和可安全删除的代码。一个默认团队、成员组合绑定、任务和审查的独立工作流模块已经纳入范围；组织树、多层 PM、跨机器组织和第二个通用编排平台暂不进入。慢速诊断先寻找耗时来源，不能把增加 Agent 数量作为默认提速措施。每项新增自动化单独核算收益，允许保留已验证切片并停止扩张。

独立第五模块和“AI 团队”导航是用户已确认的产品边界，不能再由执行 Agent 自行选择塞入 Workbench 或省略 UI。收益验证用于判断后续投入、规则范围和并发是否值得，不授权为凑架构继续扩编。此次只更新文档，不启动试点、修改客户端配置或调整日常运行实例。

用户最终需要的是更少的重复劳动、更可靠的交付和更明确的下一步。Agent 数量、自动消息数量、任务卡片数量、日报篇幅和架构完整度都不作为成功指标。

## 有价值的场景和适用边界

| 候选能力 | 可能产生的价值 | 需要验证的条件 | 当前处理 |
| --- | --- | --- | --- |
| 跨项目进度总览 | 在一处看到各项目的任务、当前阶段、执行情况、阻塞和下一步 | 任务身份和会话关联可靠，信息及时且有来源 | P0 收益试验；生产实现见 W3 |
| 交付证据检查 | 及时发现未验证的完成声明、遗漏验收项和失效测试结果 | 用户已确认需要核验负担；先量化程序检查和现有审查的缺口 | P1，P0 有用后单独验证 |
| 代码质量审查 Agent | 按用户规则检查复杂度、重复实现、未使用项和边界，并给出简化或删除方案 | 指定规则可追溯，静态告警经核验，删除不破坏行为和运行合同 | P1 的明确职责，可先独立验证工具效果 |
| 慢速诊断 | 分清时间消耗在模型请求、工具、验证、返工、依赖还是等待人工 | 能取得对应阶段的真实计时与收据，未知部分单独显示 | 首阶段采样，按瓶颈决定优化 |
| 接续当前任务 | 从进度记录恢复目标、决策、未完成项和下一步 | 当前任务版本与来源明确，既有会话恢复仍不足 | 复用 P0，不另建功能体系 |
| 独立模型审查 | 在代码质量和行为审查中补充工具无法判断的语义问题 | 改动有清晰规格、足够重要、能提供固定版本和复现条件 | 工具检查覆盖实质代码交付；模型按需深入，比较新增发现和误报成本 |
| 每日工作摘要 | 减少手工回忆，支持当日收尾和次日选择 | 用户确实会根据摘要采取行动 | 首先复用任务检查点，按需生成 |
| 自动 PM 和长期规划 | 协调多个并行目标、依赖和外部期限 | 跨项目总览和简单依赖规则仍无法减少协调负担 | 暂缓模型化调度，先采用可解释规则 |
| 多 Agent 并行改代码 | 加速可以独立交付的工作 | 任务可拆、隔离充分，集成和审查成本低于节省的时间 | 暂缓，遵守 main 开发规则 |

对于小修复、短会话和单一明确任务，当前开发 Agent 加上已有知识检索、测试脚本和按需审查，可能已经足够。重复设置 PM、开发者、测试者等模型角色，会增加上下文交接、等待和维护负担。角色名称本身不能证明能力提升。

当前仓库的 [Leader 与 GLM 协作手册](../leader-glm-workbench-playbook.md)已经要求短任务合同、独立证据、收据核对、断线恢复和避免重复派发。结合用户确认，首阶段量化这些负担的频率和净耗时，并检查已存在的能力是否正常工作，不再以单一会话接续作为主要立项依据。

Anthropic 的 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)主张从简单方案开始，并按实际效果增加复杂度；其 [多 Agent 研究系统经验](https://www.anthropic.com/research/multi-agent-research-system)也说明了协调和资源成本。这些工程经验支持先做对照试验，不能直接作为本项目或当前模型的效率收益数据。

## 建立公平的比较方法

基线包含用户当前实际使用的知识检索、上下文注入、会话恢复、计划和审查方式。先检查这些现有能力是否正常启用；若接入本身有问题，先把修复收益单独记账，不能算作新增团队的收益。

选择两到三个正在并行的日常项目，覆盖五到八项真实活跃任务，包括进行中、等待、待验证和已交付工作。保留用户现有 Claude Code 或 Codex 入口；第一轮先覆盖这些样本实际使用的客户端，不能为追求全面覆盖而先重做全部接入。不为试验制造无实际用途的功能，也不把熟悉的旧任务重复执行来测加速。

每项工作只记录以下信息，记录工具可以先用本地表格或简短文本：

- 任务类型、规模、客户端，以及使用原有方法还是试验方法。
- 从想了解全局进度到找齐活跃任务、正确说出阶段和下一步所花的人工时间。
- 从开始接续到能够确定正确下一步所花的人工时间。
- 重复解释、查找记录、检查结果、维护检查点和处理误报的人工时间。
- 是否发生遗漏验收、错误完成判断、过期信息或重复工作，以及实际修复耗时。
- 可归属的新增模型用量、费用或额度消耗；不可取得的字段标为未知，不计作零。
- 从任务被接受到交付验收的经过时间，并在可观测时区分执行、排队、等待、验证和返工；重叠区间不能重复相加。

对同类任务交替使用原有方法和试验方法，保留任务规模差异。首次试验只支持个人是否继续投入的判断，不把小样本包装成普遍效率结论。固定脚本节省的时间与独立模型审查的收益分开统计，避免把程序检查的收益归功于多 Agent。

## 第一阶段 建立跨项目现状和耗时基线

准备和整理材料的投入上限为两小时。先用已有采集、轻量会话摘要和本地简表列出样本任务，记录哪些信息能自动取得、哪些只能由用户或当前开发 Agent 确认。观察接下来至少五项正常开发任务或阶段性交付，期间保持现有开发入口和工具。

每项任务保留稳定的项目和任务标识，可关联多个会话和执行尝试。相同任务的续跑不重复建卡，Agent 委派消息不自动创建新的用户需求。把采集覆盖和任务关联缺口列出来，不能以界面数量多冒充进度完整。

每项需要接续的任务在检查点保留一张简短记录：

```text
项目与任务：项目身份、任务标识、任务标题和原始需求来源。
目标和范围：当前要完成什么，哪些内容不在本轮内。
当前阶段与状态：开发、验证或审查；运行、等待、受阻或未知。
执行关联：主开发会话、其他会话、尝试编号和最近活动时间。
当前版本：项目、工作目录、提交或工作树快照标识。
已确认决策：结论及其来源。
已验证结果：验证了什么，对应命令、退出状态和证据位置。
未完成或受阻事项：缺什么、等待谁、哪些仍未知。
下一步：下一项可执行动作及完成条件。
来源：相关会话、需求和代码引用；记录更新时间。
```

记录由当前开发 Agent 在有意义的检查点提出，沿用已有明确确认和实际结果；未确认的推断保留为候选。它是有时效的任务状态，不能自动进入长期记忆或冒充正式项目知识。先观察一份跨项目简表加检查点能否解决问题；如果已经足够，保留这种操作方式，不继续建设平台。

大改动使用“明确目标和验收条件 → 实现 → 适当验证 → 必要的独立审查 → 更新检查点”。小修改只执行适用步骤。现有授权范围内的常规工作持续推进，新增范围和确需决定的事项才升级给用户，不把流程变成反复确认。

进入下一阶段前，要有样本任务清单、状态来源、采集缺口和实际查找耗时。根据用户已确认的问题，重点判断自动更新和证据关联是否比维护简表更省力；若简单模板已经足够，保留模板并结束本轮产品开发评估。

## 第二阶段 只实现一个最小自动化试点

按 P0 跨项目总览、P1 交付与代码质量核验的顺序推进。每轮只新增一项自动化能力，前一轮的收益和维护成本可接受后再进入下一轮。代码质量工具的只读基线和规则校准可独立开展，不依赖完整团队或新界面。P2 的耗时采样从第一阶段开始，优化措施根据实际瓶颈选择，不等待完整团队成型。

每轮技术验证的开发投入上限为一个开发日，后续一轮的成本须重新列出。这是停止扩张的预算，不是生产功能完成时间承诺。超过上限仍无法在隔离环境证明可行，就记录具体缺口和新增成本，重新判断，不自动追加架构。

### P0 跨项目进度总览

用一份全局列表展示项目、任务、当前阶段、任务状态、Agent 运行状态、最新活动、阻塞原因、下一步和证据入口。需要用户处理、Agent 等待用户、已交付待验证、正常执行和信息未知分别呈现；有明确优先级或截止时间时注明来源，不自行编造紧急程度。

任务状态与会话状态分别保存。会话结束时可以显示“本轮已结束，任务待核验”，不能直接标成任务完成。长时间没有事件时核对数据来源和连接状态，不能只据此宣布 Agent 卡住或任务失败。后台任务与主回复分开跟踪。

任务须由用户明确需求或已接受任务绑定；自由讨论和相似文字不能自动合并成正式任务。关联不确定时显示待关联，不猜测百分比。一个任务可以对应多个会话，列表仍只统计一次。

Workbench 管理的会话与外部原生客户端会话的可观测能力不同。逐项核对项目身份、会话关联、执行状态和工具结果能否获取；外部对话被采集不代表拥有该客户端的实时请求队列、全部工具事件或计时。缺少的数据保留为未知，不能用 Workbench 的能力替其他客户端背书。

在新会话开始后的首个受支持上下文入口，按明确绑定返回当前任务的简短接续信息与详细记录入口，避免跨项目混入上下文。检查项目身份、当前版本和更新时间；信息不完整或版本变化时明确提示待核对。正式结论和候选信息分开，不根据 Agent 的文字声明自动完成任务。

Hook 只做有界的读取或事件交付，不在每次输入时运行模型团队。后台不可用时保留可见的失败状态并允许正常开发，不把“没有读到”显示为“没有任务”。这一试点只验证已确认可用的客户端接口，不承诺后台结果能随时插入任意客户端的进行中回复。

### P1 交付与代码质量核验

先使用确定性检查比对需求验收项、实际修改版本、可核对的工具执行收据和验证结果。每项结果注明由谁、在什么环境、对哪个版本验证。Agent 自述或自行编写的报告只作为待核验材料，不能代替真实执行证据。明确区分未运行、通过、失败、未知和已过期，禁止把会话 idle、存在 commit、截图数量或 Agent 总结单独视为验收通过。

只在验收项重要且程序检查不足时，对固定版本发起一次短上下文独立审查。审查者读取规格、修改和相关证据，默认不修改代码。已被现有检查发现的问题、样式偏好和重复意见不计为新增收益。修复由当前开发 Agent 收敛，第一版不建立自动循环修复。

#### Review Agent 的代码质量审查职责

该角色按用户指定的编码规则审查实质代码交付，围绕五个问题给出结论：新增实现是否必要、已有实现能否复用、旧路径是否仍有用途、复杂度是否合理，以及能否用更小的改动满足同一需求。它同时检查实现正确性和维护成本，必须提出有依据的简化或删除候选，或说明当前增量为何必要。

Review Agent 是团队成员，程序化质量门禁是它使用的执行基础。对于可编码的规则，程序根据固定代码、规则、工具版本和环境给出可复现的判定；Agent 负责解释、核实语义和提出整改，不能用主观结论覆盖强制检查失败。无法完全程序化的业务语义单独列为待核实，不伪装成数学证明或自动删除依据。

新增需求允许合理增加代码。质量判断看行为正确、重复路径与不必要抽象减少、复杂度受控，不以净删行数考核。小规模重复有时比增加通用框架更容易维护，审查者需要比较方案的总成本，不能为通过重复率指标继续堆叠抽象。

当前主包脚本以测试和发布校验为主。尚未为本计划安装或运行以下工具，不能据此认定当前项目已经存在某类死代码或给出已完成的质量评分。

#### 规则来源和工具选择

以用户当前明确指令、适用的 AGENTS.md、现有编码规约和工具配置确定有效规则，保留规则来源、版本和配置哈希。规则冲突时明确指出冲突；尚无既定复杂度或函数长度阈值时，先报告基线及阈值提案，不能把工具默认值冒充用户要求。

对本仓 JavaScript 和 CommonJS 代码，优先评估以下本地工具。其他项目按语言和入口单独选择适配器，不统一套用 JavaScript 规则。

| 检查对象 | 候选工具 | 审查时的用途 |
| --- | --- | --- |
| 圈复杂度、嵌套、函数长度和参数数量 | [ESLint](https://eslint.org/docs/latest/rules/complexity)及适用规则 | 按配置找出过多分支、嵌套和职责过大的函数；不同度量分别解释，不能混成一个评分 |
| 未使用文件、导出和依赖 | [Knip](https://github.com/webpro-nl/knip) | 依据配置的入口建立引用图，给出需核实的未使用候选 |
| 重复代码块 | [jscpd](https://github.com/kucherenko/jscpd) | 比较重复位置及变更前后新增克隆，帮助定位复制实现；相似不等于可以无条件合并 |
| 循环依赖和模块边界 | [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) | 检查规则禁止的依赖方向、跨层耦合和循环；结合现有模块合同判断 |

Knip 和 jscpd 当前均提供 Agent 集成入口，例如 MCP；第一轮优先使用可复现的 CLI 和结构化报告，MCP 只作为接入方式选项。工具版本、运行位置和授权范围固定后再接入，不因工具提供 MCP 就再建设一套任务系统。jscpd 的实验性语义相似功能不作为第一轮默认阻断条件。

#### 外部工具接入和多语言适配

Review Agent 的工具应可替换、可增加。通过工具适配器调用外部 CLI，或连接已有 MCP 服务，再将结果归一化供规则引擎使用。外部工具不必为每个项目写成新的 Agent；CLI、MCP 和编辑器插件只是不同接入方式，核心是能够可靠执行并读取检查结果。

用户已确认此前提到的 C++ 检查工具是 [clang-tidy](https://clang.llvm.org/extra/clang-tidy/)，它作为 C++ Review Agent 的目标工具之一。[cpplint](https://github.com/cpplint/cpplint)保留为 Google C++ 风格检查的可选补充。Google 风格根据项目明确配置，不自动强加给所有仓库。

| 项目语言或检查范围 | 可接入的工具与规则 | 能力边界 |
| --- | --- | --- |
| C++ 编码规范 | cpplint 的 Google C++ 风格检查；clang-tidy 中选择适用的 Google 约定检查项 | 检查项不能代表整份人工规约已被程序完全验证 |
| C++ 函数规模和静态分析 | clang-tidy 的 [readability-function-size](https://clang.llvm.org/extra/clang-tidy/checks/readability/function-size.html)，以及项目需要的其他检查 | 可配置函数行数、语句、分支、参数及嵌套等指标；分析所需编译参数必须完整 |
| Go | [golangci-lint](https://golangci-lint.run/docs/linters/configuration/)中的 funlen、gocyclo、gocognit、dupl、unused 等按需启用 | 分别检查长函数、圈复杂度、认知复杂度、重复片段和未使用项；不能假设它们默认全部启用 |
| 多语言函数指标 | [Lizard](https://github.com/terryyin/lizard) | 支持 C/C++、Go、Python、Java、Rust 等语言，提供有效代码行、圈复杂度、参数等指标；其轻量解析不能代替完整编译与语义分析 |
| JavaScript 和 TypeScript | 已列出的 ESLint、Knip、jscpd、dependency-cruiser | 按实际语言、入口和项目配置使用，避免工具间重复规则产生多份相同告警 |

[clang-format 的 Google 预设](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)可用于格式一致性检查，但格式化本身不能判断死代码或证明复杂度合理。各工具分别承担适合的检查职责，按项目组合使用。

每个工具适配器至少声明工具标识、固定版本、支持语言与检查能力、可执行文件和参数、项目配置、结果解析方式、退出码含义、超时与资源限制，以及是否会修改源码。CLI 优先读取 JSON、SARIF、Checkstyle 等受支持结构化输出；只有文本输出时，需要与版本绑定的解析器。支持外部 CLI 不等于任意程序都能零适配接入。

归一化结果保留项目、任务、代码快照、规则与工具版本、原始规则 ID、文件和函数位置、指标定义与单位、实测值、阈值、严重程度及证据路径。函数长度、文件长度、圈复杂度和认知复杂度分别保存，不把不同语言和不同算法的数字直接混成一个分数。最终的强制规则判定由程序完成。

结果状态区分已通过、已发现违规、执行失败、缺少运行条件、不适用和不支持。只有受支持检查实际完整执行后才可判通过，工具未安装或没有取得有效报告不等于没有问题。Review Agent 不能自行修改阈值或忽略项来改变判定。

C++ 深度检查应固定编译器、宏、头文件与目标配置，按工具要求使用编译数据库，例如 compile_commands.json；Go 检查应固定 Go 版本、构建标签和目标平台。固定规则配置的实际路径，避免不同机器意外读取用户主目录中的另一份规则。初始化、缓存和依赖准备放在隔离环境中，不能为接入工具改变日常运行实例。

第一轮接入一组实际使用的语言工具，验证原始报告、归一化、门禁判定和误报处理；新增语言时扩展适配器和项目配置，不改动任务与审查主流程。暂不建设工具市场。审查默认不使用自动修复参数，修复仍交给开发任务并按已有授权执行。

#### Review Agent 的长期记忆与审查记录

记忆组合的绑定对象扩展到用户创建的 Agent 成员。保留已有“项目绑定组合”，新增“成员绑定组合”；成员是直接绑定对象，角色用于描述职责。同为 Review 角色的两个成员可以选择不同组合，不能仅凭角色名称默认共享全部专用记忆。

每个成员具有稳定的成员 ID、名称、职责、执行配置、工具引用和记忆组合引用。成员 ID 与模型、会话 ID、执行驱动的 agentId 分开；更换模型或重新创建会话后仍能恢复同一成员的适用记忆。此处定义的是产品内成员，不是临时派发的子会话。

Review Agent 的长期规则和经确认的经验复用现有长期记忆管理及 knowledge-engine 的存储，按成员绑定及适用项目、语言选择内容。成员可以绑定多个组合，同一组合也可被多个成员或项目引用。保持同一条记忆的稳定 ID，不复制正文；无需另建一套记忆数据库。

界面在成员详情提供“记忆组合”，复用现有组合选择方式；长期记忆管理可查看组合关联的项目与成员。解除成员绑定只移除引用，不删除记忆。删除或停用成员应停止后续上下文使用，保留审查记录，并按实际删除操作处理引用；修改共享记忆时展示受影响对象。

成员在已授权项目中执行任务时，生效集合由原有适用范围记忆、该项目绑定组合中的已确认记忆，以及该成员绑定组合中满足项目和语言条件的已确认记忆组成，按记忆 ID 去重并保留来源。普通会话未绑定产品成员时，沿用原有项目规则，不借用某个 Review 成员的记忆。成员绑定记忆不授予代码修改、发布或数据访问权限。

| 内容 | 建议保存位置 | 适用对象与更新方式 |
| --- | --- | --- |
| 用户指定的审查准则、反馈方式和权限边界 | 长期记忆中的审查组合，记录明确来源 | 绑定指定的 Review 成员及适用项目；按用户确认的变更更新 |
| 共享编码规范和架构约定 | 项目规约及相应长期记忆引用 | 开发者与 Review Agent 都应读取，保持相同规则版本 |
| clang-tidy 检查项、阈值和排除项 | 仓库中的 .clang-tidy 等版本化配置 | 程序执行的权威配置；记忆保存解释和引用，避免维护另一份数值副本 |
| 已确认的审查经验、误报条件和历史整改原则 | 长期记忆的专用经验组合，或项目知识中的有证据条目 | 绑定具体成员、项目、工具版本和适用条件；条件变化后重新核对 |
| 某次审查进度、发现、报告与执行结果 | 任务和审查记录，绑定任务及代码快照 | 保存原始证据与整改历史，不自动升级为长期规则 |

记忆组合可按通用审查准则、C++ 审查经验和具体项目审查经验组织。组合名称只用于管理；可见范围由已验证的成员身份、项目授权和实际绑定控制。通用编码规则可同时分配给开发与审查成员，审查者专用的证据核对方法和误报经验只在已绑定成员的会话加载。语言和项目条件仍需匹配，不能把某个项目的历史例外推广到该成员处理的全部项目。

每轮上下文由当前任务与规格、当前有效仓库配置、适用的已确认记忆及相关项目知识共同组成。标明每条记忆来自成员绑定、项目绑定还是原有范围，便于追溯和解除。成员偏好不能自行覆盖项目强制规则，存在冲突时按当前明确要求和有效规则核对处理。

仓库规则和程序门禁保持权威。记忆中的旧描述与当前有效配置冲突时，报告冲突并追溯当前用户要求和配置来源，不凭记忆自行修改阈值、忽略项或审查标准。用户希望改变可执行规则时，应形成明确配置变更及其证据，不能仅更新一段记忆后声称门禁已经改变。

审查者新发现的可复用经验先保留为有来源的候选：包含事实、适用项目、代码或报告引用、工具与规则版本、确认状态，以及需要复核的条件。经用户确认或已明确授权的独立准入流程后再进入长期经验。Agent 的判断不能冒充用户原话或长期偏好，也不能通过自我确认把一次误报变成永久豁免。

当前安装的引擎支持按项目解析已确认记忆及记忆组合，尚未提供上述成员绑定。本计划把成员与组合的引用关系及统一的可见性解析列为新增契约，不能通过组合名称或前端隐藏伪装已实现隔离。自动注入、search/get、向量结果和文件降级读取采用同一范围校验；缓存绑定成员、项目及相关记忆和关系版本，绑定或解除后及时失效。成员身份由已绑定任务与执行会话确认，不能信任自由输入的成员名称或角色字符串。

现有长期记忆自动准入以可验证的真人来源为约束，不能为保存 Agent 审查经验而放宽这条约束。经验候选须明确作为工程观察或项目知识处理，采用独立且有证据的准入契约。在该契约完成前，经验保留在审查记录中。本次仅定义存储与作用范围，不向用户真实长期记忆写入内容。

#### 每次审查的输入和流程

1. 固定任务范围、基准版本、候选版本或未提交工作树快照、需求和有效规则。记录任务与来源；不能把其他会话或用户的既有修改误算为本次 Agent 产物。无法归属时保留未知。
2. 对完整的修改函数或文件运行适用检查，并读取基准中的对应实现。复杂度不是仅对新增几行计算。查找相关已有实现，避免只看 diff 而漏掉重复造轮子。
3. 对重复代码、未使用项和依赖图执行所需项目范围扫描。先建立一次基线，后续比较新增或恶化问题；确需全图分析时不能用只扫描变更文件冒充完整检查。
4. 质量 Agent 阅读工具结果和必要上下文，区分确定违规、待核实告警、历史债务及有理由的例外。给出最小整改方案，优先评估复用、删除旧实现、合并职责或简化控制流。
5. 将整改交回当前开发 Agent；审查者保持只读。修复形成新快照后，按影响范围复查质量与必要行为验证。结果绑定代码快照、工具版本和规则版本，代码变化后不能沿用失效结论。
6. 在同一任务上记录代码质量结论，独立于功能验证状态。只有适用的强制检查及规则都满足，才能标为已验收；工具失败、未运行或入口配置不完整时显示未完成。

检查在明确检查点、待交付或提交后的稳定快照上运行。快速规则可增量检查；图分析和克隆扫描使用适当范围并按内容与规则版本复用结果，不在每次聊天或每次保存时启动全仓模型审查，以免进一步拖慢开发。

#### 控制新增冗余和安全删除

对新的或恶化的违规优先设置门槛，未修改的历史债务单独登记。已存在的高复杂度函数若本轮确有改善，可以按有效规则保留历史例外；不能要求每项功能任务顺带重构全仓。例外应说明原因、范围和复核条件，审查 Agent 无权自行抬高阈值、扩大忽略范围或删除检查来通过验收。

未使用告警只表示候选。删除前核对 package.json 的 bin、main、exports 和 scripts、浏览器脚本入口、插件与 Hook、模块运行清单、动态加载、子进程命令和对外公共 API。[Knip 的入口说明](https://knip.dev/explanations/entry-files)及[问题处理指南](https://knip.dev/guides/handling-issues)可用于校准入口和误报。

本项目的四个固定 npm 模块、运行清单、必要公开入口、可复用测试工具和真实项目及知识数据受现有合同保护，不能因没有普通静态 import 或某次扫描的未使用告警而删除。已有产品兼容路径须核对仍支持的版本和调用方，不能由模型自行宣布过期。

源码、测试、生成文件和安装副本分开配置。排除 node_modules、生成产物和本地报告可以减少噪声，但不能把所有测试代码排除后声称项目没有重复；也不能删除独立验证所需的测试，或把不同测试的断言抽成与实现同构的共享逻辑来降低分数。

删除候选需要给出引用调查、行为影响、最小修改范围和验证方式。实际删除由开发任务执行并保留可追溯 diff；需要保持兼容或尚无法证明无用途时，先列候选及缺失证据，不自动批量清理。

#### 审查报告和试点判断

每条有效发现至少包含规则及来源、文件位置、基准与候选版本、工具证据、对行为或维护成本的影响，以及最小整改方案。建议删除时，说明保留哪条实现、哪些调用需要迁移、如何验证功能未受损；不只输出“过于复杂”或“建议重构”。

任务摘要分别展示功能验证与代码质量状态，详情保留必要新增项、已核实的简化或删除候选、历史债务、例外和待核实项。代码增减行数、复杂度和克隆变化仅作辅助指标，不作为单独成功标准。

先对一到两项真实代码修改验证这组工具和规则是否能给出可操作结论，再扩大 P1 样本。记录新增实质发现、被采纳的简化、误报和漏报、审查耗时、额外模型用量，以及整改后行为验证情况。若反馈主要是样式偏好、重复已有检查，或引入的抽象和等待超过收益，则收缩规则与模型审查范围。

### P2 慢速诊断和定向优化

先抽样观察至少五次用户认为慢的执行阶段，记录可取得的时间和活动来源。表内各项都是待验证原因，当前没有判定其中哪项是用户实际瓶颈。

| 待区分原因 | 需要的证据 | 确认后优先采取的措施 |
| --- | --- | --- |
| 等待模型响应或服务排队 | 客户端或执行器可取得的请求起止、错误、限流和排队记录 | 检查供应商与配置；按任务复杂度评估模型选择，不能靠增加 PM 解决 |
| 重复读取、重复解释或上下文膨胀 | 重复工具活动、相关性、输入规模及重复重建上下文的记录 | 缩短任务合同，提供准确知识入口和版本化检查点，减少重复全文注入 |
| 构建、测试、检索或文件操作慢 | 对应工具的真实运行时长和资源活动 | 优化实际慢命令；保持必要验证，不通过删验收或伪报结果换速度 |
| 多个任务争用资源 | 并发数、实际排队及 CPU、内存、磁盘或供应商限额的只读观察 | 调整可配置并发，重任务错峰；并发阈值由测量决定 |
| 等待人工、依赖或确认 | 明确等待原因、开始时间和解除条件 | 把待处理项集中显示，优先提示能解除阻塞的事项 |
| 返工、重复派单或协调开销 | 同一任务的尝试链、重复交付和返工原因 | 明确验收条件、检查派单幂等、缩减不产生有效成果的审查和交接 |

无法观测到的模型内部推理和等待不得从聊天间隔推断。没有可靠来源时记录总经过时间和已知区间，其余标为未知。耗时区间可重叠，不能简单求和作为完整耗时分解。日常健康长任务不因时间长而自动中止。

提速按实际端到端交付和已验证产出衡量。先优化占比最大的已知瓶颈，再对同类任务比较；不承诺通过增加 Agent 缩短单任务时间，也不把少跑验证、转移等待或拆碎任务数算作提速。Claude Code 的 [官方性能排查文档](https://code.claude.com/docs/en/troubleshooting)可作为客户端诊断入口，具体措施须对照实际环境，不在本计划中直接执行会话重启或配置修改。

### 试点的集成范围

复用 Workbench 的执行入口、Event Bridge 的采集事实和 knowledge-engine 的读取能力，先验证端到端正确性。能力归属和写入契约尚未明确时，使用隔离的小型原型，不在外壳中临时堆放生产任务业务。

正式产品采用已确定的独立工作流服务，保留现有四模块；任务主数据及页面不放入 Workbench。手工基线阶段可以只用短记录，不要求提前建完整服务。首版不增加数据库或整套第三方编排框架，不能因收益观察自行改变已确认的模块归属。

正式 UI 新增“AI 团队”主导航，由工作流包提供任务、成员、工作流、工具与接入四页签；首页和项目页投影摘要。当前已有[界面与记忆组合计划](memory-combinations-ui-recovery-delivery-plan-20261111.md)，应与在途工作协调；不新增组织图、自由画布或第二套任务主库。跨项目总览和接续共用任务记录。

## 第三阶段 真实使用后的后续投入评估

每轮观察五个工作日。P0 至少覆盖两个项目、五项活跃任务和八次实际进度查询或任务切换；P1 至少覆盖五项适合检查的实际修改。慢速诊断至少有五次执行阶段样本。自然样本不足时延长观察，不能为凑数制造任务。

以下数字是建议的试点去留标准，不是已有测量结果。开始试点前固定口径，不能看到结果后反复降低门槛。

| 维度 | 建议判断标准 |
| --- | --- |
| 全局进度效果 | 在一分钟内正确找到样本中全部活跃任务的当前阶段、阻塞或下一步；同类进度查询和任务切换人工时间中位数减少至少 30% |
| 关联和覆盖 | 样本任务不漏项、不重复计数、不串项目；无来源的状态明确为未知，补录负担计入成本 |
| 净时间收益 | 按实际发生频率估算，每周净节省至少一小时；已扣除维护、读摘要、纠错和误报处理时间 |
| 交付检查效果 | 比程序检查和原有审查增加可复现的实质发现，或使同类人工验收时间减少至少 20%；同时记录遗漏和误报 |
| 代码质量效果 | 发现并核实新增重复路径、不必要抽象或未使用候选；整改后行为与必要契约保持有效，新增和恶化的强制违规得到处理；同时核对误报、审查成本和是否为降低指标反而增加抽象 |
| 速度改善 | 对同类工作记录端到端耗时和验收质量；针对最大已知瓶颈的优化以阶段耗时减少至少 20% 为候选目标，未观测到改善就不宣称整体开发提速 |
| 信息可信度 | 不出现把未知或未验证内容标为已完成的情况；发生一次就暂停相关自动状态更新并修正 |
| 额外投入 | 用量可追踪、模型调用有上限、不让日常开发等待长时间后台分析；无可信用量数据时不扩大自动调用 |
| 回本周期 | 时间型功能按本轮实测净收益计算，开发与集成投入预计八周内收回；超出时优先继续使用简单模板 |

净时间收益计算为：进度查找、任务切换、接续、重复解释和验收实际节省的时间，减去维护、补录、额外阅读、纠错、误报及额外等待时间。避免重复计入同一段时间。运行时间变短、人工注意力减少和已验证交付增加分别报告，不能混成一个效率百分比。

发现缺陷可能很有价值，但“避免未来多少小时事故”先作为质量收益备注，不能冒充已经测得的节省时间。高影响缺陷的证据可以单独支持保留按需审查，由用户按实际风险判断，不能据此默认启动所有任务的模型审查。

例如，若开发集成共花十六小时，每周净省一小时，回本约十六周。这只是计算示例，不能算作当前试点收益；在这个结果下，应缩减投入，而非继续扩展团队。

后续投入建议分三种：达到门槛则评估新的扩展；只有部分任务受益则建议按类型启用；未证实净收益则建议限制后续投入。以上作为报告交用户决定，不自动取消已授权的实现、回归、安装验证和发布准备。

## 后续团队建设的进入条件

先交付已确认的跨项目进度、交付证据、程序检查和交付检查点触发的独立 Review。若这些仍不能减少优先级冲突与人工协调，再评估新增模型协调角色；真实任务有可独立交付的部分，且串行集成成本可控，才评估多个开发 Agent 并行。

默认组织维持“跟随原生会话的开发成员 + 程序记录与检查 + 后台 Review 成员”。该角色通过工具检查和有依据的减法审查履职，模型对需要语义判断的修改按需深入。生产化中的身份权限、队列、任务锁、恢复、接口适配、客户端兼容和维护成本已计入主计划；其他角色只有在现有方式持续不足时再增加。

用户另提出后续添加“版本与文档维护”成员，已单列主计划第 15 节及执行手册 D0–D3。其收益按规范/示例过期问题、修复耗时、可实际运行的调用和版本漂移遗漏衡量，不按文档篇数衡量。它复用同一工作流成员系统，不阻塞当前 W0–W8，也不授权自动发布或直写知识引擎产物。

Paperclip 可参考任务和执行治理，mattpocock/skills 可参考规格与审查步骤，Superpowers 可参考调试和验证方法。每项引入都应指出当前哪条失败记录需要它解决，保留版本与适配记录；开源项目的流行度不作为立项依据。

## 执行约束和交付物

本仓库和相关模块按 AGENTS.md 在 main 开发，保留用户及其他 Agent 的未提交工作。遵守现有分包边界和固定依赖，不把独立模块源码复制回外壳。上游默认创建分支或 worktree 的技能须先适配，不能原样执行。

日常安装及其模块保持运行。生命周期测试必须选择独立安装前缀、数据、知识目录、配置和端口；只管理当前试点创建且已确认归属的进程。原型启停不改变日常安装或原生 Hook 信任记录。发布、升级和替换运行实例按用户已有的明确授权处理，本计划不包含这些操作。

真实任务原文、个人配置、使用记录和测试输出保存在源码外或被忽略的本地位置；可复用工具和必要回归测试进入 Git。生产接入后，用户可以直接停用试点，任务和知识数据仍保留可读，客户端回到原有开发方式。

每阶段给出中间进展：发生了什么负担、使用了什么方法、测得多少收益和成本、错误或缺口，以及未来投入建议。报告后自动继续当前交付的下一项可执行工作，不停下等待“继续”。分开回答“是否看清全部任务”“是否更容易核验交付”“是否减少维护成本”“是否缩短开发时间”；未知如实保留，不能以样本不足代替技术测试，也不能据此提前终止用户要求的全部交付。
