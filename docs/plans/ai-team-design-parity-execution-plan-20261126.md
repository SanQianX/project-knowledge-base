## 六、数据模型与迁移

### 6.1 维护域升级到第 2 版

`state.maintenance` 从单仓库改为登记表加多仓库状态，键名不变，加 `schema: 2`。

```text
state.maintenance = {
  schema: 2,
  repos: { <repoId>: {
    repoId, projectId, root,            // root 只来自受信转发
    branch, remote, allowPush,          // remote 是远端名称
    overrides: { <toolId>: 参数覆盖 },
    scope,                              // digest(projectId, root) 前 24 位，沿用 0.2.3 的算法
    uses, workspaceReady,
    busy, active, hold, waitReason,     // 每个仓库一份
    remotes: [], branches: [],          // 登记时读取，可手动刷新
    revision, createdAt, updatedAt } },
  tools: { <toolId>: {
    toolId, name, access, output,       // access: read | write；output: json | exit
    timeoutSeconds,
    invocation: { cli: { program, args } | mcp: { serverId, operation, arguments } },
    check?, repair?,                    // 可选的阶段专用调用
    revision, updatedAt } },
  mcpServers: { <serverId>: { serverId, name, program, args, revision } },
  jobs: { <jobId>: {
    jobId, title, memberId, toolId, repoIds,
    trigger: { kind: manual | commit | daily, at },
    access: read | write, delivery: report | candidate | push, rounds,
    enabled, revision, updatedAt, lastSchedule: { <repoId>: 日期 } } },
  runs: [{ runId, jobId, repoId, stage, status, access, delivery, trigger,
           baseSha, commitSha, deliveryResult, workspace: { kind, path, reused },
           loadedMemory: [{ groupId, name, revision, memoryIds, truncated }],
           logs: [{ at, title, detail }], receipts: [],
           queuedAt, startedAt, finishedAt }],
  inflight: { <runId>: { pid, repoId, access } },
  commitKeys: { "<jobId>:<repoId>:<sha>": runId }
}
```

运行状态增加 `unchanged`（无改动）。`stage` 取 `work` 或 `writeback`。

成员记录增加 `authorizedToolIds`、`authorizedRepoIds`。修复执行器复用现有的 `driverId`（`codex`、`claude` 或空）和 `model` 字段。角色字段保留在数据里，界面不再编辑，新成员默认 `developer`。

维护任务上限从 12 提到 50，已结束运行的上限从 100 提到 300，`commitKeys` 随运行一起裁剪。

### 6.3 迁移

服务首次以第 2 版启动时，在一个事务里完成导入，此前备份 `state.json`：

1. 读取 0.2.3 的 `maintenance.json`：项目变成一条仓库记录，工具迁入 `tools`，占用、保护、等待原因和工作区标记一并迁入。
2. 旧任务补 `repoIds`、`access: write`、`rounds`；旧运行补 `repoId`。
3. 写入 `schema: 2` 和导入来源。原 `maintenance.json` 不修改、不再读取。

工作区目录和候选引用的命名空间不变，已有的维护 worktree 直接复用。任务、审查收据、会话绑定等任务域数据一律不动。

回退到 0.2.3 时，旧代码因为 `scope` 不匹配而拒绝维护操作并给出明确错误，不会静默重置。需要彻底回退时用备份文件恢复。

## 七、调度与执行规则

1. **并行**：全局同时运行的运行数不超过 `maxParallel`，默认 3。
2. **同仓串行**：写运行同一仓库同时只有一个，占用该仓库的维护 worktree。
3. **只读快照**：读运行不进 worktree。用临时索引文件加 `git checkout-index` 从基础提交导出一份不含 `.git` 的快照，运行结束即删除。
4. **开发占用**：写运行遇到占用、保护状态、原工作区有未提交改动或进行中的 Git 操作时留在队列，并显示等待原因。
5. **去重与合并**：同一任务同一仓库已有排队中的运行时，新触发把它的基础提交更新到最新；已有运行中的运行时，新触发另排一个。
6. **定时**：按任务乘仓库记当天是否已排程，北京时间。
7. **提交触发**：事件匹配到已登记仓库后，为包含该仓库的提交触发型任务排程。
8. **写回等待**：推送型运行生成候选提交后如果仓库被占用，回到队列并标记 `writeback`。空闲后重新取远端最新提交、重跑工具和复检，再推送。
9. **恢复**：重启时进程已不在的写运行记为中断并进入保护，读运行只记为中断。清理遗留快照。

写任务的执行流程，轮次不超过任务的 `rounds`：

```text
检查（工具）
  ├─ 通过 ──────────────────────────────┐
  └─ 有问题 → 修复（成员的执行器，或工具自带的修复命令）→ 再检查 …
                                         └─ 工作区无改动 → 无改动
                                            有改动 → 验证（再检查一次）→ 候选提交 → 按交付方式推送
```

修复轮次用尽或仍不通过，运行标为「需要处理」。步骤标题沿用设计稿，其中设计稿的「Agent 修复」在产品里叫「修复」。

## 八、工具接入

**本地命令**

- 程序必须是绝对路径，参数是数组，不经 shell。占位符只允许出现在参数里：`{worktree}`、`{baseSha}`、`{branch}`、`{memoryFile}`。
- 上下文继续经标准输入传 JSON（`ai-team-maintenance/v1`），与 0.2.3 的工具兼容，另加记忆文件路径和已加载记忆的组合。
- 结果约定：`exit` 表示 0 通过、1 有待处理项、其余失败；`json` 要求标准输出是含 `status`（`pass`、`findings`、`error`）和 `summary` 的 JSON 对象。

**MCP 工具**

- 模块运行时不能引入 npm 依赖，用标准库实现最小的 stdio 客户端：换行分隔的 JSON-RPC 2.0，`initialize`、`notifications/initialized`、`tools/call`；服务发来的其他请求一律回「方法不支持」。
- 每次运行启动一个服务进程，放在数据目录下的空目录里，不放进维护 worktree；结束时关闭，超时则结束进程树。
- `json` 取 `structuredContent`，没有就把文本解析为 JSON；`exit` 把 `isError` 视为失败。
- 「探测」真实启动服务并列出工具名，整体限时 8 秒。

**权限的含义**

「只读」是声明加运行后核对，不是沙箱。本地进程以当前用户身份运行。本期能保证的是：只读运行在不含 `.git` 的快照里执行；运行前后比对仓库引用，被改动就标为「需要处理」并进入保护。工具登记弹窗写明这一点。

## 九、模型修复

新增修复适配器 `src/repair-native.js`。审查适配器的只读约束不动。

**执行器**：先做 Codex，验证通过后做 Claude Code。成员的 `driverId` 决定用哪个，`model` 可选。

**启动方式**：固定参数数组，不经 shell，工作目录是维护 worktree，提示词经标准输入传入。按本机 codex-cli 0.137.0 和 Claude Code 2.1.143 的帮助输出，调用形态如下，执行时以真实 CLI 为准再核对一遍：

```text
codex exec --sandbox workspace-write -c approval_policy="never" --ignore-rules --json
      --output-schema <运行目录>/repair-schema.json --output-last-message <运行目录>/repair-result.json
      --cd <维护 worktree> [-m 模型] [-p 配置档] -

claude -p --output-format json --json-schema <文件> --permission-mode acceptEdits
      --tools "Read,Edit,Write,Grep,Glob" --strict-mcp-config --mcp-config <空配置>
      --setting-sources "" --no-session-persistence [--model 模型]
```

Claude 默认不给 Bash 和网络工具，Codex 的沙箱默认断网。

**提示词**：成员的职责提示词、已加载的记忆、检查工具给出的问题清单、范围约束（只修这些问题、不提交、不动无关文件）。输出是经 Schema 校验的 JSON：改动的文件、摘要、未解决的问题。

**约束与证据**

- 入口必须存在并通过版本探测；显式指定的模型必须在允许清单里；模型身份取自运行自身的输出，不在清单内则本轮不采纳。
- 修复后核对 HEAD 仍等于基础提交；改动文件数和差异大小超过上限判为「需要处理」。
- 修复是否成功只看复查工具的真实退出码或结构化结果。
- 入口缺失、未登录、额度不足、超时都如实记为失败并给出原因，不切换到其他模型。
- 环境变量用白名单，只保留系统、主目录和认证需要的项。凭据不进日志。
- 进程管理复用维护运行器的 `execute()`（进程树结束、输出上限、中止信号）。

**真实验证**：在隔离仓库的临时 worktree 上各跑一次真实修复。这会消耗少量 Codex 和 Claude Code 额度。CLI 不可用时如实记为未验证。

- 外壳拉起模块时传入引擎地址（`KB_KNOWLEDGE_ENGINE_URL`，与它拉起 Workbench 的做法一致）。模块新增轻量的 `MemoryProvider`。
- 读取路径：`GET /api/memory-groups/:id` 取组合所属的脑区和版本，再 `GET /api/memories?groupId=&brainId=&status=confirmed` 取已确认的记忆，跟随游标。
- 授权：只读取本次运行的成员当前已启用、且在它的 `memoryGroupIds` 里的组合。模块持有成员主数据，读取前自己校验。不改引擎包：引擎自带的成员绑定存储在生产中尚未接线。
- 有界：按策略文件的字符预算截取，默认 6000。超出部分在记录里标 `truncated`。
- 记录：运行记录里保存组合 ID、名称、版本和记忆 ID。本模块不存储记忆正文。
- 去向：写入运行目录下的临时文件，供修复提示词引用，并经 `{memoryFile}` 和标准输入上下文提供给工具，运行结束删除。
- 界面：运行详情的「调用工具」步骤显示「已加载记忆 A、B」。
- 引擎不可达时运行照常进行，步骤里记「记忆未加载」。

## 十一、安全与授权

步骤 1 先做前三项，之后的步骤才允许登记工具。

1. **Host 校验**：外壳对 `/api/workflow/*` 的写请求，回环监听时只接受 `127.0.0.1`、`localhost`、`[::1]` 带端口的 Host。现状下 Origin 和 Host 都可被 DNS 重绑定控制。
2. **`Sec-Fetch-Site`**：浏览器带了这个头时，写请求只接受 `same-origin` 或 `none`。
3. **Origin 转发**：外壳把校验过的 Origin 转发给模块，模块的新写接口要求它存在且等于知识库页面的来源。直接来自本机进程的调用仍按回环连接和本地 Host 放行。`POST /consumer/drain` 纳入同一道门。
4. **仓库登记走受信转发**：外壳按已登记项目解析 Git 根，附运行令牌再转发（`src/module_bridge/module-bridge.js:299-349` 的做法）。解析不到就拒绝。页面上不能手填路径。
5. **成员授权在服务端校验**：任务的工具和仓库必须在成员授权范围内；只读任务只能调用只读工具且只能「仅记录结果」。授权撤销后任务显示「工具授权需更新」「项目授权需更新」「工作区权限需更新」，不再触发。
6. **删除保护**：工具被任务引用时不能删；仓库被任务引用或有排队运行时不能删；移除仓库时 worktree 不干净就保留并显示路径。
7. **审计**：工具、MCP 服务、仓库、成员授权的每次变更写入现有的变更流水。
8. **界面输出**：工具输出、运行日志、路径按文本渲染。
9. **外壳全局加固**（步骤 8）：把第 1、2 项从 `/api/workflow/*` 扩大到外壳全部路由，可用环境变量追加允许的 Host。

## 十二、接口变更

模块接口保持 `apiVersion v1`，全部为新增。前缀沿用 `/api/workflow/v1/maintenance`，现有的来源检查自动覆盖。

| 方法与路径 | 说明 |
| --- | --- |
| `GET /maintenance` | 看板数据：仓库、工具、任务及状态、最近 50 条运行摘要、计数、策略生效值 |
| `GET /maintenance/runs`、`GET /maintenance/runs/:runId` | 分页运行列表；运行详情（步骤、收据、已加载记忆） |
| `POST /maintenance/repos`、`PATCH`、`DELETE /maintenance/repos/:repoId` | 仓库登记（只接受受信转发）、配置、移除 |
| `POST /maintenance/repos/:repoId/refresh`、`…/control` | 重读远端和分支；占用标记与解除保护 |
| `POST`、`PATCH /maintenance/tools`、`DELETE /maintenance/tools/:toolId` | 工具登记 |
| `POST`、`PATCH /maintenance/mcp-servers`、`DELETE`、`POST …/:serverId/probe` | MCP 服务登记与探测 |
| `POST /maintenance/jobs`、`DELETE /maintenance/jobs/:jobId` | 任务 |
| `POST /maintenance/runs` | 立即运行 |
| `GET /maintenance/executors` | 修复执行器的就绪状态 |

`GET /overview` 增加 `automation` 摘要计数，供首页卡片使用。成员接口的请求体增加 `authorizedToolIds`、`authorizedRepoIds`。

能力开关只增不改：`multiRepoMaintenance`、`toolRegistry`、`memberAuthorization`、`memoryLoading`、`agentRepair`、`mcpTools`。

前端拆成两个脚本：`ui/app.js`（外壳、共享代码、成员、工具）和 `ui/automation.js`（任务调度、项目与工作区、运行记录）。打包白名单、静态路由表和两个冻结的契约测试同步更新。

## 十八、风险与未验证项

- 现状描述来自读代码。真实 CLI 的可写沙箱在 Windows 上的实际行为、模型身份在输出里的位置，都要在步骤 6 用真实 CLI 验证。现有审查代码按更新的 Codex 版本写过取值路径，本机是 0.137.0。
- 入口形式（`.exe`、`.js` 还是 npm 的 `.cmd` 垫片）影响进程启动方式，步骤 6 确定。
- Event Bridge 是否把登记的 journal 列表当作投递过滤条件没有核实，步骤 2 在隔离环境用真实 Bridge 验证。
- 只读快照的导出方式、Windows 下结束 MCP 进程树，分别在步骤 2、7 用真实进程验证。
- 引擎的记忆读接口不要求令牌，依赖回环监听。
- 任务详情失去界面入口后，现有两个进行中任务只能在对话里查看。
- 范围大、跨多个会话。每一步的提交和阶段记录是恢复点。
- 顺带发现、未列入的问题：`PATCH /team` 的版本比较用的是聚合版本号；模块页发送 `kb:ready` 早于数据加载；知识库 README 有三处过期描述。
