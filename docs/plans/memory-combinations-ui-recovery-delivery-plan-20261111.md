## 阶段一 冻结功能规则和页面职责

1. 首页：全局需要人工处理的事项最多预览 3 条，候选最多预览 3 条，记忆组合最多展示 4 个入口；总数覆盖全部项目。自动恢复中的任务单独显示，不算人工待办。
2. 长期记忆：左侧组合，右侧独立小记忆；提供全部记忆、未归组合、候选箱、正文搜索与分页。内容编辑、组合改名/删除只保留一个明确入口。
3. 项目：全局搜索、领域筛选和分页列表；可拖组合到项目，也可通过按钮/复选框操作。项目详情展示引用组合与去重后的生效记忆。
4. 知识检索：复用真实检索 API，支持项目范围和知识/记忆类型；结果能查看真实正文和来源。不以预览中的 includes 搜索替换现有召回与排序。
5. 活动记录：按全部、自动恢复、需处理、已完成、操作记录查看。列表是摘要，展开才读取完整运行详情；成功、等待、失败、数据未读到分别呈现。
6. 设置：保留真实外观、后台模型供应商、默认模型、外部 Agent 接入和必要系统诊断。预览为了体验而简化的假配置不能替代这些功能。
7. 去掉“开始工作”导航不等于删除 Workbench 服务。它仍参与维护模型配置等运行链路；模型供应商管理必须能从设置独立打开，不能再跳到已移除的 work 页面。
8. 项目分页默认可用 20 条；预览的 8 条只是演示布局。记忆/候选默认每页 10–20 条，组合列表多时支持查找。每页大小和性能目标在实施记录中固定。

组合与删除规则在本次实现中按下表执行：

| 操作 | 结果 |
| --- | --- |
| 新建一条记忆 | 一个 ID、一个标题和完整正文；段落和换行留在同一记录 |
| 把已有记忆放入其他组合 | 新增引用，不复制正文，不换记忆 ID |
| 项目挂载组合 | 新增项目到组合的引用，可跨领域，重复挂载不产生重复关系 |
| 从一个组合移出小记忆 | 只移除该关系；其他组合和原记忆保留 |
| 从项目移除标签 | 只解除这个项目的关联，其他项目保留 |
| 删除组合 | 解除引用并删除组合；其中的小记忆保留在全部/未归组合中 |
| 删除小记忆 | 从全部组合移除该记忆，使用 tombstone/现有删除语义保留必要审计 |
| 编辑共享小记忆 | 更新同一记录，展示影响范围；后续上下文使用新版本 |
| 确认候选 | 人工确认后成为正式记忆，可选加入组合；不自动挂载到其他项目 |

“通用约定”是组合名称，不自动等同于全局强制范围。新组合默认没有项目引用。不要通过静默复制、正文相似度自动合并或自动修改作用域来伪装复用。

完成条件：接口、删除影响、遗留范围兼容、重试分类和分页约定形成可测试的契约。后续不能通过放宽断言绕过这些规则。

## 阶段二 实现引擎中的记忆与组合关系

主要修改私有 `knowledge-engine` 的 `src/memories.js`、`src/store.js`、`src/server.js`，按需拆出小型关系和查询模块；引擎继续满足主仓库要求的零 npm 依赖运行边界，不为此引入数据库、前端框架或 CDN。

1. 保留现有记忆 ID、text、originalText、来源事件/hash、evidence、确认状态和时间。新增独立 title；正文沿用既有 text 或提供明确兼容映射，不按换行拆记录。
2. 建立组合实体：稳定 ID、brainId、name、revision、时间与删除标志；建立组合到 memoryId、projectId 到 groupId 的唯一关系。
3. 项目登记和领域归属继续由主仓库注册表负责，引擎使用已有受管项目投影验证引用。不要建立第二套互不一致的项目注册表。
4. 定义“旧作用域记忆”和“通过组合应用的记忆”的明确区分。新组合记忆不能因为 scope 字段缺失，被旧 `scopeOf()` 默认当成 global。
5. 原有 global/domain/project 记忆继续按原规则生效。界面可将其显示为原有全局/领域/项目记忆；加入组合不会隐式扩大或缩小原范围。转换为仅按组合生效须是明确操作。
6. 所有增删关系校验同一 brain、项目/组合/记忆存在且未删除、记忆已确认、重复关系幂等。禁止跨智脑绑定、路径输入替代对象 ID、候选提前注入。
7. 单次批量关系变更在同一事务或等效原子存储操作中完成，包含 revision 校验。并发写同一关系时返回 409 或合并明确的幂等增删，不能用旧快照覆盖新修改。
8. 删除组合/小记忆使用一次明确确认；可逆解除关联不弹多层确认。若提供撤销，后端应具备真实恢复操作及冲突检查，不能只把前端 DOM 恢复。
9. 保留与修改 memory materialization、共享索引和检索的写入边界；所有文件仍经过 RuntimeLayout、安全路径与现有原子写入/锁机制。
10. 为大记忆规定字符上限和清晰校验错误，但不因字符预算在存储时截断正文。上下文预算不足时返回未注入/待按需读取状态，完整正文仍能检索/读取。

完成条件：使用引擎 API 能完成真实 CRUD 和跨项目引用，重启后仍然存在；重复引用只指向一个记忆记录。

## 阶段三 实现数据迁移和有效记忆解析

1. 在隔离目录中建立旧版样例：三种作用域、候选/忽略/删除状态、缺少 title 的老记录、多行大正文、非标准历史 ID、来源依据及失效目标。
2. 在设计时确定 schema 版本、备份与旧引擎兼容策略。迁移必须在受控 writer lease/锁下建立一致性快照，校验后原子提交；每次迁移有版本和校验记录。
3. 迁移只增加模型必需字段和关系，不复制正文，不自动确认候选，不重建或挪动真实项目/知识目录，不丢原始表达与 tombstone。缺 title 时仅生成展示标题，正文原字节保留。
4. 迁移重复执行应无额外变化。中断后从完整旧状态或完整新状态恢复，不能得到半套组合关系。
5. 新增唯一的“该项目当前有效记忆”解析服务：原有范围适用集合，加上项目绑定组合中的已确认记忆，按 memoryId 去重并保留所有来源关系。
6. 上下文注入、普通检索、向量召回、MCP search/get、文件降级读取、UI 生效清单均使用相同的可见性判断。不能只改 UI 标签或正常注入，而让全文/get/旧索引旁路读到已解绑记忆。
7. 关联版本要纳入有效集合缓存和上下文 session 缓存失效。即使正文未改，绑定/解绑/删除组合也会改变集合；旧向量记录回传时必须重新校验当前引用关系。
8. 对正在执行的模型请求/维护任务保留启动时快照；下一次上下文准备使用新关系。已存在于模型对话里的文本无法物理撤回，后续使用现有记忆增量机制发送更新或移除信息，不重写历史会话。
9. 保留当前“一次会话首次索引、后续记忆增量”的能力，不能退回每轮全量注入。记忆删除/解绑产生移除增量，暂时落盘不可读不能误当删除。
10. 保留旧范围优先级和用户当前指令优先规则。组合只组织引用，不根据组合名称强加权重；冲突不静默改写正文或自动合并。
11. 对旧版本读取新 schema 的行为做实测。若旧版本不能安全读取，必须明确拒绝而不误读新组合为全局；回退时恢复迁移前备份，不能承诺切回旧二进制后直接读新数据。

完成条件：迁移前后遗留项目的生效集合一致；新绑定只影响目标项目；所有读取入口对解绑、删除和未确认状态的判断一致。

## 阶段四 增加可分页查询和真实业务 API

以下路径是拟定契约，实施前可按现有路由规范统一命名；一旦确定，补充请求、响应、错误、分页和 revision 测试。浏览器通过主程序现有同源代理访问引擎，不能得到 runtime token 或访问运行配置私有接口。

| 资源 | 拟定能力 |
| --- | --- |
| `/api/engine/memory-groups` | 分页查询、新建组合 |
| `/api/engine/memory-groups/:id` | 详情、改名、删除组合 |
| `/api/engine/memory-groups/:id/members` | 增删 memoryId 引用，校验 expectedRevision |
| `/api/engine/memory-groups/:id/project-bindings` | 查询引用项目，按 addProjectIds/removeProjectIds 原子修改 |
| `/api/engine/projects/:id/memory-groups` | 项目引用组合查询和幂等增删 |
| `/api/engine/projects/:id/effective-memories` | 分页返回去重集合、来源组合和遗留作用域来源 |
| 现有 `/api/engine/memories` 与单条 CRUD | 扩展标题、多行正文、候选确认，保持旧客户端兼容 |
| 引擎 overview 与主程序首页 overview | 聚合全局任务/候选计数，合并主程序接线、模块连接等事项 |
| 主程序项目列表查询 | 基于现有注册表做全局搜索、领域过滤、稳定排序和分页 |

逐步实现要求：

1. 在服务端筛选全部匹配对象后分页，返回真实 total/nextCursor 和数据版本；前端不下载全部任务/项目再假分页。
2. 全局待办不能通过“最近 50 条任务”筛选得到。后台直接统计全部未解决事项，单独返回少量预览和进入全部列表的 cursor。
3. 批量关联采用“新增 IDs + 移除 IDs + 基础 revision”的差量提交。未浏览的分页记录保持原关系；不能把当前页未勾选的对象当作全局取消。
4. 一个共享服务/模型故障只产生一个根因待办，列出影响项目数，不给所有后续等待任务重复报错。项目内队首失败造成的等待显示依赖状态。
5. 现有 aggregated/projection、旧 API 和其他模块调用保持兼容。新 UI 逐步切到分页端点，不直接改旧响应为只有第一页。
6. 读取失败返回明确错误或 partial/freshness 状态。首页不能把失败、超时、未加载、空结果全部显示成“没有待办”。
7. 搜索与分页游标绑定 brain、筛选条件和稳定排序，参数变更后重置游标；异步旧响应不能覆盖新项目/新筛选状态。

完成条件：API 用 1000 个项目和超过 100 条历史任务的样例证明全局计数、旧异常、分页和并发关系修改正确。

## 阶段五 实现有上限的自动恢复

主要修改引擎 `src/coordinator.js`、`src/analysis-failures.js`、`src/index-request.js`、必要的 worker 错误边界和持久化字段。不要把“retryable=true”直接理解为无限自动重试；当前认证失败、余额不足等也会被标成可再次执行。

1. 保留结构化错误的类型、HTTP 状态、Retry-After、失败阶段、请求标识等安全字段。继续脱敏，不把供应商原始输出、密钥或请求头写进状态/日志。
2. 建立恢复分类：临时网络/服务故障、限流等待、配置/余额阻塞、数据与安全校验失败、未知错误。不能根据自然语言包含某个词就作最终判断。
3. 建议初始默认：首次失败后最多自动重试 3 次，基础间隔 10 秒、30 秒、120 秒，加入少量抖动；尊重更长的 Retry-After。另设总耗时和资源预算，覆盖 SDK 内部重试，避免两层重试相乘。参数在契约中固定并由虚拟时钟测试。
4. 401、明确鉴权失败、余额不足、必要模型配置缺失、损坏数据或越权写入不进行短间隔循环。配置阻塞可由真实配置同步成功事件唤醒；没有可靠额度恢复信号时，不声称自动发现了充值。
5. 维护已晋升而索引失败时，只重试索引阶段；分析/晋升已完成不能重新执行。网络超时导致结果不明时，先检查原任务/claim/晋升状态，再决定是否重发。
6. 持久化 attempt、nextRetryAt、分类、阶段、最后错误、恢复原因及预算。进程重启后重新装载等待任务；使用可关闭、可去重的调度器，不给每个任务叠加无主 setTimeout。
7. 复用现有 FIFO、同项目互斥、跨项目并发、claim、writer lease 和原子晋升。自动重试、手动重试、配置恢复和重复事件不能同时派发同一个阶段。
8. 同一供应商故障时控制并发、做共享退避/熔断；恢复后逐步放行，不能把所有项目一起冲向模型服务。
9. 未完成的队首任务继续阻塞本项目后续依赖，其他项目按其可用条件继续；不得通过跳过失败提交自动推进分析头来伪造恢复。
10. 生命周期关闭时取消调度、等待已开始的受控写入落稳；不触碰任何外部用户服务。模拟时钟测试不需要实际等待数分钟。
11. UI 分别显示“自动恢复中”“等待配置”“需要处理”“已完成”。只有不能自行恢复或达到预算才计入人工待办；解决后退出待办，历史记录保留。

完成条件：注入“一次失败随后成功”的故障后，无人工点击即可完成；持续失败按预算停下；恢复不会重复分析、重复晋升或丢失队列顺序。

主仓库实际稳定发布入口是 `.github/workflows/publish.yml` 的 `stable-prepare`、`stable-publish-next`、`stable-promote`。不要按旧手册推 `vX.Y.Z` 期待自动稳定发布。

1. 将引擎精确版本、lockfile、manifest、UI、测试和版本清单纳入最终提交。只提交本任务授权的文件，记录最终 `$CoreSha`、`$CoreVersion`。
2. 最终提交重新通过六项非发布 CI。后面任何业务、依赖或清单改动都使该验收 SHA 失效，必须重新执行相应门禁。
3. 读取官方 registry 的当前 latest、next 和旧版本 SRI，记录为基线；不要使用计划编写时的 5.0.32 当成未来必然的 latest。
4. 调用 `stable-prepare`，等待完成并下载 `stable-next-candidate`。核对其 source SHA、版本、依赖、package files、文件数量、SHA256 和 SRI；对该 tgz 在隔离前缀执行预发布安装/启动与 UI 检查。
5. 使用已审阅 receipt 中的 prepare run ID 和完整 hash 调用 `stable-publish-next`。本阶段只发布已准备的同一 tgz，不重建，不改 latest。

```powershell
gh workflow run publish.yml --repo SanQianX/project-knowledge-base --ref main -f mode=stable-prepare -f package=@sanqianx/project-knowledge -f "source_sha=$CoreSha" -f "expected_version=$CoreVersion"

gh workflow run publish.yml --repo SanQianX/project-knowledge-base --ref main -f mode=stable-publish-next -f package=@sanqianx/project-knowledge -f "source_sha=$CoreSha" -f "expected_version=$CoreVersion" -f "prepare_run_id=$PrepareRunId" -f "expected_tarball_sha256=$CoreSha256" -f "expected_tarball_sri=$CoreSri" -f "reviewer=$ActualReviewer"
```

6. 从官方 registry 重新下载/安装这次 next 版本，不能拿源码目录、node_modules 链接或本地 tgz 代替官方包验收。核对下载 SRI 与 prepare receipt 完全一致。
7. 用空用户 npm 配置和独立前缀做全新安装，确认无需访问私有 GitHub 源码、无需 npm 登录即可获得公开依赖；检查引擎版本和四模块哈希。
8. 用真实旧官方版本在隔离前缀建立升级样例，再升级到该官方候选。样例包含设置、项目、旧全局/领域/项目记忆、来源证据、知识正文、候选与 tombstone。保存安装前后字节哈希；首次启动迁移变更要有明确差异清单。
9. 对官方候选完整执行本计划的核心浏览器链路、真实 API、同目录停止/重启、自动恢复重启、插件/MCP 上下文、搜索和保护日常实例检查。测试 start/status/stop 都明确 `--data <测试目录>`。
10. 复用 `desktop/test/release-browser-5025-smoke.cjs` 的 CLI 生命周期/四模块验收和升级保留工具，增加本功能场景。`--provenance` 是标签，不能把传入“official”字符串当作官方下载证明。
11. 收集官方版本的截图、API/回归报告、包哈希、配置/知识保留证明、日常实例前后身份与健康，形成一次可审阅的验收结果。现有工作流中需要真实验收声明的字段必须如实填写，不能编造人工验收或用预览的 42 项检查替代产品验收。

完成条件：公开 next 候选可安装，升级保留和真实业务链路通过，所有证据对应同一包版本/源 SHA/SRI。任何失败均保持旧 latest，不强行晋升。

## 阶段十一 更新主包 latest 和完成发布验证

1. 再查 registry latest，确认仍等于候选验收时记录的 `$OldLatest`。若别人已发布新版本，重新协调，不能覆盖较新 latest。
2. 满足官方安装、UI、重启验收门禁后，用现有 stable-promote 调用更新 latest；不重新发布 tarball，不移动 engine latest，不变更其他三个模块标签。

```powershell
gh workflow run publish.yml --repo SanQianX/project-knowledge-base --ref main -f mode=stable-promote -f package=@sanqianx/project-knowledge -f "source_sha=$CoreSha" -f "expected_version=$CoreVersion" -f "expected_tarball_sri=$CoreSri" -f "expected_current_latest=$OldLatest" -f acceptance_ack=official-next-install-ui-restart-passed -f "reviewer=$ActualReviewer"
```

3. 跟踪到终态并下载 `stable-promotion` receipt。确认官方 latest=目标版本、next 未被意外改变、SRI 未改变。
4. 再在全新隔离前缀不指定版本安装 `@sanqianx/project-knowledge`，验证默认安装拿到新版本，API/UI/引擎依赖符合这次结构。测试中可以用 `--prefix <独立前缀>`，不能覆盖用户全局安装。
5. 检查旧主包和旧引擎仍能下载，原有版本的 SRI 不变；不 unpublish，不删除历史 release，不移动已公开发布的 tag。
6. 最后确认日常实例的主进程与模块身份、端口和健康保持一致。发布完成不自动执行用户机器上的全局安装、stop、restart 或数据迁移。
7. 交付 release receipt，至少包括两个仓库 source SHA、包版本、准备/发布/晋升 run ID、官方 tgz SHA/SRI、CI 与验收报告、迁移/保留结果、已知限制和回退说明。

完成条件：正常用户的默认安装可以获取真实新功能，旧版本仍可用，日常实例没有因为开发测试或发布被中断。

## 阶段十二 故障回退和收尾

1. 若只在 next 阶段失败，保持 latest 不变，修复后发布新的候选版本。不要覆盖已上传版本或为隐藏失败删除历史。
2. 若晋升后发现严重问题，按本次发布的受控回退范围记录影响、当前 tag 与 receipt，完成并发基线检查后将主包 latest 指向已验证旧版本。只回退本次变更的标签，不擅自变更其他包或 npm 授权。撤回 tag 不会回滚用户已安装的程序或已迁移的数据。
3. 对已经启动并迁移数据的安装，按阶段三验证过的兼容性/备份方案回退。不能直接让旧引擎读不支持的新 schema；不能对仍在运行的真实数据目录做文件覆盖恢复。
4. 回退日常实例的程序和数据属于独立的真实安装操作，必须有用户明确指令和停写安排；本功能发布不包含这项操作。
5. 所有测试仅清理本次创建且归属可证明的进程。保留失败报告，不按端口、node.exe 名称或全局命令清扫。
6. 清理临时目录前验证绝对路径属于本次测试根；不清理真实 project/knowledge 数据、固定依赖、runtime manifest 或其他 agent 的文件。
7. 更新交付说明与当前状态：已开发、已测试、已发布 next、已晋升 latest 分开列明。不能将“界面可点”写成“真实数据迁移和恢复已通过”。

## 给执行 agent 的启动指令

> 在 `main` 上按照本计划完成五页简化 UI、独立多行小记忆与组合引用、跨项目应用、数据兼容迁移、统一有效记忆解析、全局分页待办和有上限的自动恢复。参考预览只用于交互，不复制其中假业务数据或自动成功计时器。先核对工作区他人改动、在途版本和日常实例保护基线。先完成引擎与迁移/可见性/恢复测试，再接主程序和浏览器回归；引擎通过现有 GitHub Actions OIDC 发布 next，主包固定精确引擎版本后按 prepare → publish-next → 官方安装验收 → promote 更新 latest。正常发布不要求用户 npm login，不新增 Token 或发布身份。保留旧版本、配置、知识及原作用域。不停止、重启、替换日常知识库或任何日常模块，不全局覆盖安装，不覆盖其他 agent 工作。交付真实测试报告、官方包哈希、发布记录和可执行回退步骤。

## 实施记录应保留的项目

- 基础提交、在途改动归属、最终两个源码 SHA 与版本。
- 对原型的必要调整，以及实际 API、schema、作用域、缓存和恢复策略契约。
- 每个阶段的完成状态与对应提交；所有失败、修复与未通过的验收。
- 单元/API/浏览器/迁移/升级/规模/兼容回归结果与证据位置。
- 引擎、主包的官方发布/晋升 receipt 和默认安装证明。
- 日常实例的保护结果，以及尚未执行的真实安装升级事项。
