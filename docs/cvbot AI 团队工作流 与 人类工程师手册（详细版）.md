## 2. 组织架构与角色定义

| 角色                 | 组成                         | 职责                                                         | 落点                       |
| -------------------- | ---------------------------- | ------------------------------------------------------------ | -------------------------- |
| **CI 组**            | 全 AI（PM + 执行者），无人类 | 每日监控自动编译、自动测试、自动版本发布。**只监控与告警，不修复** | 构建机（★未接 federation） |
| **PM**               | AI（leader）                 | 按产品线统筹多个仓库 agent：设计验证方法、设计持续交付流程、提高稳定性；对接人类 leader；协调跨仓库问题；仲裁知识库冲突 | 持续交付电脑               |
| **仓库负责人 agent** | AI                           | 一仓库一个：复现每个有价值的提交、补测试、维护规格、确保质量。**发现问题只向自己的 PM 汇报** | 持续交付电脑               |
| **资源管理者**       | AI                           | 测试资料（现场图像/日志/配置/配方快照）统一**接收·校验·归档·分发**；维护不可变副本、清单与索引；规划存储与备份；**主责目录分配**；资源变化主动通知消费方 | cf-cd-02                   |
| **Test Contactor**   | AI                           | 开发者与资源管理者之间的**接口人**：把测试需求与资源分发到执行侧，回收汇总结果，转达问题 | cf56-01（开发者电脑）      |
| **CVBot 维护者**     | AI                           | 本机 cvbot 更新调试维护、团队运行环境；处理一切 cvbot 相关问题；守发布产线 | cf-cd-01（运维机）         |
| **开发者 agent**     | AI                           | 直属人类开发者：开发 feature、debug、调代码；**权限跟随开发者**（资深直提/资浅发 PR） | 开发者本机                 |
| **人类工程师**       | 人                           | 用 cvbot 开发；对接本产品线 PM；**spec 评审是全链路唯一人类质量闸门** | 开发机                     |

## 3. AI 团队工作流（分角色详解）

### 3.1 入口与自治链路（一切从这里开始）

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`① 提需求：开发者 ──(PM 群)──▶ 对应产品线的 PM② 交资料：开发者 ──(本机 WebUI 文件传输)──▶ Test Contactor ──▶ 资源管理者                                        ↓                            资源管理者校验 → 归档 → 登记清单/索引                                        ↓                    ③ 主动通知所有消费方 Agent（各仓库负责人）                                        ↓        ┌──────────────── AI Team 内部自治 ────────────────┐        │  PM 派单 → 仓库负责人执行 → 结果/问题汇报回 PM    │        │  发现问题 → 发 PR（不直接改人类仓库）             │        └──────────────────────────────────────────────────┘                                        ↓                              ④ 结论回到人类（PM 对接）`

**关键点**：资料一交，编排、执行、汇报、结论回传全部在系统内完成，人类不需要在 AI Team 内部流转时介入。

### 3.2 三大闭环（系统的心脏，缺一不可）

**闭环① 测试闭环**

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`仓库负责人复现提交 → 补测试用例(进测试仓库)→ 开发者 agent 开发时必跑这些用例（新功能/bugfix 不引出新问题）→ 测试失败/新发现 → 反馈回负责人更新用例→ 用例越来越密，回归保护越来越强`

**闭环② 知识闭环**

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`日常开发中人与 Agent 的大量决策（需求背景、规格来龙去脉）→ cvbot cron 每日定时把会话蒸馏进知识库（library-update 技能）→ 知识库指引开发判断（kb_lookup 按锚点检索，新工程师快速掌握规格）→ 仓库负责人依据沉淀做出更好的测试→ 规格不断沉淀、相互成就`

**闭环③ 现场资料闭环**

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`人类交付现场资料（样品照/缺陷图/复现资源）→ Test Contactor → 资源管理者校验、归档、登记索引→ 主动通知相关仓库负责人→ 负责人创建真实场景回归测试（更高保真 → 更早发现真实问题）→ 资料沉淀为组织资产（外面找不到的护城河）→ 客户需求沉淀进需求库（intent/，原话引用+日期，append-only），驱动产品迭代`

### 3.3 PM 工作流

| 时机            | 动作                                                         |
| --------------- | ------------------------------------------------------------ |
| 每工作日        | 巡检各仓库负责人的复现队列（阻塞？资料不足？）→ 协调；跨仓库问题派单 |
| 收到告警        | CI 红了 → 督促负责人定位；负责人升上来的问题 → 派单或升给人类 |
| PR 48h 无人响应 | 提醒开发者；72h 资浅 PR 无人 review → 提醒资深工程师         |
| 每周            | 与人类 leader 开周会：质量问题、PR 处理情况、知识库增长、下周重点；**批量审核知识库 draft 条目 → active** |
| 每月            | 组织历史缺陷族回溯（L3）+ 向人类 leader 提质量趋势报告       |
| 仲裁            | 知识库条目冲突、跨仓库问题归属、测试策略分歧（争议条目人类确认） |

### 3.4 仓库负责人（CD agent）工作流 —— 复现 · 测试 · PR · 沉淀

**分层复现，不是每个提交都深挖：**

| 层     | 对象                            | 动作                                  |
| ------ | ------------------------------- | ------------------------------------- |
| L1     | 全部提交                        | CI 编译 + 已有测试（自动，红绿即知）  |
| **L2** | **修复类提交**（fix/修复/缺陷） | **深度复现 + 补测试**（五步细则见下） |
| L3     | 历史缺陷族                      | 每月专项回溯                          |

**L2 深度复现五步：**

1. **读提交，回答三个问题**：解决什么问题（缺陷现象）？什么情况下产生（触发条件：输入/状态/时序）？修复正确性依赖什么假设？——提交信息里的验证故事（如 `32_gui1px 单 item area=3 gd=-15 OK→NG`）就是现成的用例规格。

2. **构造复现条件**：优先**合成图**（cv::Mat 程序化生成，可重复、小体积）；合成不出的真实缺陷形态 → 向人类要现场资料；**红绿验证：用例必须先在修复前代码上跑红，再在修复后跑绿。禁止恒真测试**。

3. **写测试，进测试仓库**：落点 `<模块名>-tests` 仓 `unit/` 桶，`TEST(模块名, 场景描述)` 命名；断言可判定（精确值/区间/状态断言），**禁止"不 crash 就算过"**；加 `.cpp` 自动进 GLOB，不改构建系统。

4. 发现代码问题 → 发 PR（必须带证据）

   ，PR 固定三段式：

   ![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/readme.svg)markdown

   ​

   `## 问题     <这段代码在什么情况下有问题——具体触发条件>## 证据     <复现步骤/测试输出/缺陷图像对比>## 确认逻辑 <为什么这是问题而不是特性——引用 KB 条目或客户需求>`

   人类确认后合入，CD 不直接改人类仓库。

    

   48h 无人响应 → PM 提醒。

5. **沉淀**：测试用例本身即沉淀；复现中的发现（边角行为、规格模糊处）→ 知识库条目草案（status: draft，PM 审核升 active）；规格缺口（"这事没定过规格"）→ 标记升给 PM → 人类确认。

**禁止事项**：❌ 不经人类确认修改人类仓库（只发 PR）；❌ 写恒真测试；❌ 用"代码风格"类小问题骚扰开发者（聚焦行为缺陷）；❌ 把现场图片直接提交主仓库（进测试仓 `data/` 或资产库）。

### 3.5 CI 组工作流 —— 每日监控（无人值守）

**每日节奏：**

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`06:00  拉取全部仓库最新代码（repo-rs sync）06:10  逐仓库构建（Windows / 告警基线）07:00  跑各测试仓 unit 桶（ctest -R unit）08:00  汇总日报 → 发飞书群 + 落盘全天   监听 push 事件（增量构建 + 测试）发版日  验证版本号/产物完整性 → 发布报告`

**每日日报模板**：构建矩阵（仓库×分支×构建×测试红绿）+ 异常与趋势（失败数、已通知谁、测试增长）+ 版本发布校验结果。

**告警与升级：**

| 事件               | 动作                                                         |
| ------------------ | ------------------------------------------------------------ |
| 构建失败           | 自动重试 1 次（排除网络抖动）→ 仍失败：通知 CD PM + 责任人类工程师（飞书 + Gitea issue） |
| 测试失败（回归）   | 定位到具体用例 → 通知 CD agent（负责复现定位）→ issue 记录   |
| 测试失败（新缺陷） | 同上，标记 `new-defect`                                      |
| 发布产物异常       | **立即通知人类 leader（阻塞发布）**                          |
| 磁盘/资源不足      | >80% 预警，>95% 阻塞构建                                     |

**CI/CD 分工（重要）**：CI 发现红、CD 定位修；CI ❌修代码 ❌补测试，CD ✅发 PR ✅补测试；发布执行 CI ✅，发布内容决策**只有人类能定**。

**禁止事项**：❌ 修复代码或测试（只报告）；❌ 跳过失败直接标绿；❌ 告警通道外私发个人消息（统一走群 + issue）。

### 3.6 资源管理者工作流

- **接收**：测试资料统一入口（来自 Test Contactor 的联邦文件传输，SHA-256 校验）；
- **校验**：完整性、格式、元数据（哪个客户、哪条产线、什么缺陷、谁拍的——**没有元数据的图是垃圾**）；
- **归档**：维护**不可变副本**；小图（<1MB）进测试仓库 `data/`，大图集进资产库；主责存储规划与目录分配；
- **登记**：清单与索引，消费方可检索取用；
- **通知**：资源位置或状态变化时**主动通知所有消费方 Agent**；
- **清扫**：inbox 保留 7 天自动清扫（保留期限策略是开放问题）；
- 异常/缺失 → 标记 → 通知提交方与消费方 → 必要时升给 PM。

### 3.7 Test Contactor 工作流

- 把测试**需求**与**资源**分发到执行侧 Agent；
- 回收并汇总测试结果，转达执行侧遇到的问题；
- 是开发者↔资源管理者之间的**接口人**：开发者不直接找资源管理者。

### 3.8 CVBot 维护者工作流

- 本机 cvbot 的更新、调试与维护（sw-updater 自更新、发布仓 checkout）；
- 处理一切与 cvbot 相关的信息与问题——**维护整个团队的运行环境**，不属于任何业务线；
- 守发布产线：`snow-ball/cvbot`（源码）→ CI 构建 → `drone/cvbot-release`（Git LFS 发布仓）→ 各机器 checkout + 每 24h 更新检查。

### 3.9 开发者 agent 工作流

- **直属人类开发者**，权限跟随开发者（资深可直提主仓，资浅走 PR）;
- 一开发者可开**多 session + git worktree 并行开发**（`spawn` 工具带 worktree 参数：每张票一个 worktree 一个分支，工具不负责创建/删除 worktree——那是显式的 `git worktree add/remove`）;
- 开发时**必跑**测试仓库沉淀的用例（回归保护）。

### 3.10 支撑机制（这些是上面一切的地基）

- **federation**：`cvbot-hub` 独立进程只做**花名册**（Agent↔地址，无 LLM、不转发流量，实例拨入）；`cvbot-gitea` 独立进程收 Gitea webhook、验签后 fanout 给 agent（TriggerFrame）；agent 间委派协议：`propose → accept/decline → ask/answer → progress → note → report → abort`；安全机制：签名凭证、防重放窗口、白名单、通道预算、入站闸门、**对齐闸门**（接单前必须复述任务）；

- **知识库**：每主仓一个 `<主仓短名>-KB` 独立仓，submodule 挂主仓 `knowledge/`；KB 分支与主仓挂载分支同名（v320-dev → KB 也 v320-dev，禁默认 main）；append-only（改错=新条目引用旧条目）；`kb_lookup(symbol)` 按锚点检索，四态回答 `found/uncovered/unknown/unchecked`；

- **权限模型**：

  ​

  | 变更对象                      | 谁可写               | 谁可合入           |
  | ----------------------------- | -------------------- | ------------------ |
  | 人类工程师的仓库              | AI 只发 PR           | 人类               |
  | 资浅开发者                    | agent 改完 → PR      | 资深 review 后合入 |
  | 资深开发者                    | agent 可直接提交主仓 | 开发者本人         |
  | Agent 自营仓（测试仓/文档仓） | agent 直接修改       | agent              |

  ​

- **事实/主张/意图三登记**：`PRODUCT.md`（运营者简报，唯一常驻意图，≤2KiB）；`MEMORY.md`/`HISTORY.md`（按 session 隔离的事实与流水账）；`intent/`（用户原话带日期引用，append-only，supersedes 制）；**用户意图是引用不是事实，模型推断永不记成用户说的**。

## 5. 人类工程师如何工作

### 5.1 一天的样子

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`早上  看 CI 日报（构建红绿）→ 看有没有仓库负责人发来待确认的 PR上午  开发：跟开发者 agent 走流程（grill-me → to-spec）      ★ 拿到 spec 后交给主管/资深工程师 review —— 批准才能往下做      批准后：to-tickets → implement-spec（每张票自动走 TDD）下午  提交 / 发 PR → 处理仓库负责人的 PR 评论随时  现场资料（样品照/缺陷图）→ WebUI 上传 → 经 Test Contactor 到资源管理者周五  周会：质量/PR/知识库一览（PM 汇报）`

### 5.2 开发链五步（你怎么参与每一步）

![img](https://zcode.z.ai/remote/v4/3.16.2/material-icons/document.svg)text

`grill-me → to-spec → ★人工review ⛔ → to-tickets → implement-spec → code-review → 合入`

**第 1 步 · grill-me（盘问澄清）**：agent 把你的设计映射成决策树，一轮轮只问"前沿"问题、每个问题带推荐答案，**查代码/查环境是它的活**（它派子 agent 去查，不拿"我不知道"烦你），直到没有任何东西被默默假设。**你要做的**：认真回答每个问题——你答"是"就等于认可它的建议，口误会被固化。**判断标准：这个改动半年后还需要人理解吗？需要，就值得走全流程。**

**第 2 步 · to-spec（写规格）**：不采访、只综合。产物含问题陈述、用户故事、实现/测试决策、范围外；会**先画出测试的"缝"（seam）**并和你确认——测试只写在公共边界上，复用已有缝、选最高的缝。产出发布到 issue tracker（自动打 `ready-for-agent` 标签）+ 作为知识库输入。

**第 2.5 步 · ⛔ 强制人工评审（无例外）**：spec 必须交主管/资深工程师**批准**才能进 to-tickets。评审五看：问题陈述对不对、用户故事全不全、测试的缝选得对不对、范围外清不清、与已有规格/ADR 冲突没说明理由没有。**为什么这么硬**：spec 是源头，源头错了后面每一步都在错误方向上高质量执行，而且看起来很完备——比明显出错更危险。**spec 的最终责任在人，不在 AI。** 评审有意见 → 回 grill-me 或直接改 spec → 重新提交。

**第 3 步 · to-tickets（拆票）**：拆成曳光弹式垂直切片（每张票穿透所有层、独立可验证、一个上下文窗口装得下、声明阻塞边）形成任务图；**拆完会跟你过一遍粒度和阻塞边，你批准才发布**。宽重构例外：按 expand–contract（先加新形态→分批迁移→删旧）排序。

**第 4 步 · implement-spec（并行实现）**：每张票派一个全新子 agent 在**独立 worktree**里跑，内部调用 tdd 技能（红先于绿、一次一片、期望值来自独立事实来源、禁 mock 内部协作者/同义反复断言/横向切片）；按阻塞边持续派单保持最大并发；完成合并回集成分支后统一 code-review。**你要做的**：等结果，或中途用 `/stop` 打断。

**第 5 步 · code-review（双维度）**：两个并行子 agent 分别审 Standards（符合本仓编码标准）和 Spec（符合发起它的 issue/spec），修完标 PR ready。

### 5.3 你要主动做的三件事（手册的灵魂）

1. **跑测试**——别等 CI 红。本地开发时测试仓库的用例就是你的安全网；
2. **沉淀**——grill 里做出的判断（为什么这么做、客户怎么说的），确认进了知识库（每日定时自动整理，随时也可以让它记）；
3. **交现场资料**——样品照、缺陷图、复现资源，WebUI 上传 → Test Contactor → 资源管理者。**你见到了才有，交上来全组受益**：它会变成真实场景回归测试，下一次你的代码就被这些测试保护。

### 5.4 与 AI 侧打交道速查

| 场景                            | 怎么做                                                       |
| ------------------------------- | ------------------------------------------------------------ |
| 需求/质量问题找谁               | 找**本产品线的 PM**（BS 或 TF），PM 再对接人类               |
| 仓库负责人发来 PR               | 看证据 → 同意合 / 不同意评论说明                             |
| 想让某类场景有回归测试          | 告诉 PM，或直接发 issue 说明意图                             |
| 现场资料交付                    | 本机 WebUI 上传 → 经 Test Contactor → 资源管理者             |
| 不信任 agent 改的代码           | code-review 逐块对照 spec 审；资浅 PR 本来就要人审           |
| 我的 agent 和仓库负责人什么区别 | 你的 agent 是你的同事（权限跟你）；仓库负责人是别的部门的质检（只向 PM 汇报，不直接找你）。改代码都走正常 PR |

### 5.6 常见疑惑

- **"五步流程太重，小改动也要？"** —— 小 fix 可直接 implement + 跑测试；但任何要写进 `docs/` 的决定都值得 spec。标准：*半年后还需要人理解吗？*
- **"多个 agent 同时改代码会不会打架？"** —— 不会，前提是走 implement-spec：每张票自己的 worktree，最后才合并。手工让两个 agent 改同一棵工作树才会打架。
- **"我的会话别人能看到吗？"** —— 不能。但每日知识整理会把**值得沉淀的结论**进知识库。MEMORY.md 是按 session 隔离的。
- **"AI 直接改我的仓库吗？"** —— 永不。只发带证据的 PR；你的仓库只有你能合入。
